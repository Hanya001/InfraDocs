# 2026-11-23 TE 缓存身份修复与验证

## 问题

vLLM Ascend 的 `AscendPostGradPassManager` 覆盖了 TorchNPU 安装的全局 post-grad pass 槽，导致 `TeSourcePinPass` 没有进入实际 pass 链。仅恢复该 pass 仍不够：外层 vLLM 缓存会先按 `InductorAdaptor.compute_hash()` 选择目录，随后直接读取旧的 `vllm_compile_cache.py` 句柄，不会重新计算 pass UUID。

本轮实测也复现了这一点：AOT 冷启动后加入 `TeSourcePinPass`，暖启动仍从原目录 `881984f2ec/backbone` 直接加载旧 FX 句柄。因此修复同时覆盖内层 pass UUID 与外层 compiler hash。

## 实现

### vllm-ascend

在 `AscendPostGradPassManager.configure()` 中无条件恢复 `TeSourcePinPass`，用 `CallableInductorPass` 包装，并将原生 bytes UUID 转为 hex。它不依赖融合或 elide 开关。

### torch_npu

在 TE `_activate()` 中幂等安装 `CacheBase.get_system` 包装。仅在 `TORCHINDUCTOR_NPU_BACKEND=triton_experimental` 时，将 TorchNPU 版本和 `_te_source_digest()` 加入 system factors，并按原排序 JSON + SHA-256 公式重算 hash。这样外层 `InductorAdaptor.compute_hash()`、普通 FX 缓存目录以及 Inductor 内层身份都包含相同指纹；非 TE 后端保持原返回值。

Triton Ascend 不另加重复因子，现有 `triton_key()` 已覆盖其身份。

## 验证

- vllm-ascend `test_inductor_track_fusion_chain.py`：`11 passed`。
- TorchNPU `test_package.py` 与 `test_te_source_pin.py`：`24 passed`。
- 新增测试覆盖 pin UUID 委托、聚合 UUID、非 TE 不变、TE digest/TorchNPU 版本变化、外层 `InductorAdaptor.compute_hash` 变化和安装幂等。
- 真实 installed TE `config.py` 追加一行无害注释后，新进程结果：
  - `CacheBase.get_system()["hash"]`：`e43efcbf...` → `93acc260...`；
  - `InductorAdaptor.compute_hash(None)`：`df61367dac` → `c8ea1d64ff`；
  - 恢复文件后两者均回到原值。
- 恢复后源码与 installed `config.py` 一致，site-packages drift 检查为 `PASS（FAIL 0 / WARN 0）`。
- 最终代码的 Qwen3-0.6B AOT 冷启动重新编译并保存产物；下一次新进程在新外层目录 `7ea1374c2d/backbone` 直接加载 FX 句柄及 AOT model，`VLLM_FORCE_AOT_LOAD=1` 下生成成功，两个请求 token 与冷启动一致。外层修复前使用的目录为 `881984f2ec/backbone`。

## 边界

- 默认自动生成的 vLLM 缓存目录已覆盖。用户显式设置 `compilation_config.cache_dir` 时，上游会绕过自动目录隔离；本轮没有扩展为另一套索引校验机制。
- 同一进程内修改 TE 文件不会清除 `get_hash_for_files` 的进程级缓存，验证必须跨进程。
- AOT 的 model 容器可能仍被反序列化，但 finalize 会使用新的外层 compiler hash，不再读取旧 FX 句柄。新增配置字段本身也会改变 AOT 配置哈希，因此最终代码需要重新保存一次 AOT 产物。
