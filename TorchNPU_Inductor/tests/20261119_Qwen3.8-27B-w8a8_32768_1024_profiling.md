# Qwen3.8-27B-w8a8 32768/1024 Profiling 与修复验证

日期：2026-11-19。

## 1. 目的

针对 Qwen3.8-27B-w8a8 在长上下文负载 32768/1024 下的 Inductor 性能回退，采集 default 与 Inductor 的 prefill/decode 小范围 profiling，定位主要差异。

## 2. 环境与负载

- 机器：a5-25，Ascend950DT，原始 profiling 使用 NPU 3、4，修复验证使用 NPU 0、1，均为 TP2。
- 模型：`/mnt/weight/Qwen3.8-27B-w8a8`。
- default：`AscendCompiler`。
- Inductor：`inductor + triton_experimental`。
- 两条路径均为 MRV2、`FULL_AND_PIECEWISE`，复用原性能测试编译缓存。
- 8 条并发流式请求，每条输入 32768 tokens、输出 1024 tokens，`temperature=0`、`ignore_eos=True`、`return_token_ids=True`。
- 输入由固定 seed 生成，两条路径使用相同 token ID 序列。

## 3. 采集方法及合理性

预热请求不进入 profiling。正式请求使用流式响应中的 `token_ids` 精确计数，不按时间或文本长度估计。

- Prefill：发起 8 条请求前开始采集，8 条请求都收到首 token 后停止。
- Decode：8 条请求都达到 128 个 token 后重新开始采集，都达到 256 个 token 后停止。
- 停止传播存在少量延迟，因此计数可能高于阈值；这些实际计数被保存，用于审核。

| 路径 | prefill 停止时计数 | decode 开始时计数 | decode 停止时计数 |
|---|---|---|---|
| default | 32, 15, 27, 23, 19, 11, 7, 3 | 157, 140, 152, 148, 144, 136, 132, 128 | 286, 269, 281, 277, 273, 265, 261, 257 |
| Inductor | 31, 26, 22, 18, 14, 10, 6, 2 | 157, 152, 148, 144, 140, 136, 132, 128 | 286, 281, 277, 273, 269, 265, 261, 257 |

两条路径的 8 条请求均完成 1024 tokens，无请求错误。每个 rank 的 prefill 和 decode 分别生成独立 `*_ascend_pt` 目录。

- default 每个 rank 的 prefill/decode 原始 trace 约 277/147 MiB。
- Inductor 每个 rank 的 prefill/decode 原始 trace 约 260/145 MiB。

## 4. 主要结果

以下数据来自 `op_statistic.csv` 和 `kernel_details.csv`。表中的总耗时是设备执行时间累计值，不等于端到端时间；不同算子可能存在重叠。

### 4.1 Prefill 的关键异常

Inductor 生成了 `triton_unk_fused_add_npu_dynamic_quant_npu_rms_norm_0` 融合内核。default 中没有这个内核。

以 rank0、相同形状 8192×5120 的逐次记录直接比较：

| 路径与算子 | 次数 | 平均单次耗时 | 累计耗时 |
|---|---:|---:|---:|
| default：`RmsNorm` | 32 | 48.03 μs | 1.537 ms |
| Inductor：`...fused_add_npu_dynamic_quant_npu_rms_norm_0` | 32 | 374.22 ms | 11.975 s |

rank1 复现了同量级耗时。该异常足以解释事件驱动采集中 Inductor prefill 明显变慢。

### 4.2 其他主要 prefill 算子基本持平

rank0 的汇总数据：

| 算子 | default 累计 | Inductor 累计 | Inductor/default |
|---|---:|---:|---:|
| QuantBatchMatmulV3 | 7656.697 ms | 7651.300 ms | 0.999 |
| FusedInferAttentionScore | 3365.101 ms | 3356.168 ms | 0.997 |
| ChunkGatedDeltaRuleFwdH | 1546.805 ms | 1546.691 ms | 1.000 |
| HcclLaunchAicpuKernel | 275.938 ms | 298.077 ms | 1.080 |

因此，本次回退不是量化矩阵乘、注意力或 ChunkGatedDeltaRuleFwdH 普遍变慢导致的。HCCL 有约 8% 差异，但绝对增量远小于异常融合内核。

### 4.3 Decode 也有该内核，但绝对影响较小

rank0 decode 窗口中：

- FusedInferAttentionScore：default 1304.604 ms，Inductor 1304.585 ms。
- QuantBatchMatmulV3：default 646.380 ms，Inductor 645.774 ms。
- HcclLaunchAicpuKernel：default 648.491 ms，Inductor 633.783 ms。
- Inductor 的异常融合内核：128 次，累计 67.655 ms，平均约 528.56 μs。

decode 的主要注意力和量化矩阵乘基本持平；该融合内核带来额外开销，但绝对增量明显小于 prefill。

## 5. 对融合内核的检查

### 5.1 与 default 原生算子的区别

以下均为 rank0 prefill、8192×5120 相关记录：

| 路径与算子 | 输入 | 输出 | Block Num | 平均耗时 |
|---|---|---|---:|---:|
| default：`RmsNorm` | BF16 的 8192×5120 输入和 5120 权重 | BF16 的 8192×5120 输出，以及 FLOAT 的 8192×1 倒数标准差 | 64 | 48.03 μs |
| default：`AddRmsNormDynamicQuantV2` | 两个 BF16 的 8192×5120 输入和 5120 权重 | INT8、INT8、BF16、FLOAT、FLOAT | 64 | 104.37 μs |
| Inductor：生成的 `...fused_add_npu_dynamic_quant_npu_rms_norm_0` | BF16 的 8192×5120 输入和 5120 权重 | 两个 BF16 的 8192×5120 输出 | 64 | 374222.77 μs |

Inductor 中 `AddRmsNormDynamicQuantV2` 仍然存在，平均耗时 104.27 μs，与 default 的 104.37 μs 基本一致。因此异常不是原生量化融合算子被替换后变慢，而是额外生成的 RMSNorm 类内核异常慢。

### 5.2 实际 launch 参数与 tiling

通过 launcher 动态 trace 和生成代码共同确认，8192×5120 prefill 内核的实际配置为：

- `XBLOCK=4`，`R0_BLOCK=5120`，`num_warps=16`。
- `real_block_x0=4`，`x0_blocks=2048`，实际 `grid_0=2048`。
- 每个 program 处理 4 行，形成 `[4, 5120]` 的二维 tile，并对输入做两遍遍历。
- `kernel_details.csv` 中的 Block Num=64 表示使用的硬件核数，不是 launcher 的 grid，不能据此推断重复计算。

codegen 的 `npu_dispatch_recipe` 与 launcher 实际 grid 一致，没有重复处理或漏发 tile。仅改变 tile、warps 或 launcher 形式不能解释全部结果，后续单变量实验进一步定位到了编译期常量标记。

### 5.3 单变量对照实验

以下独立测试均使用 8192×5120 BF16 输入，输出与 PyTorch 浮点参考计算比较。除表中明确修改的变量外，其余生成代码和运行环境保持一致。

| 实验 | 平均耗时 | 数值结果 |
|---|---:|---|
| 原始 Inductor 内核，常量标记 `r0_numel=5120` | 约 378.6 ms | 部分配置有明显错误 |
| 一行一个 program，自定义 launcher，保留常量标记 | 981.9 ms | 后 3072 行错误 |
| 一行一个 program，Triton 标准 launcher，无常量标记 | 0.174 ms | 最大误差 0.03125 |
| 一行一个 program，自定义 launcher，去掉常量标记 | 0.203 ms | 最大误差 0.03125 |
| 原始 4 行 tile，自定义 launcher，去掉常量标记，固定原配置 | **0.092 ms** | 最大误差 0.03125 |
| 原始 4 行 tile，自定义 launcher，去掉常量标记，正常自动调优 | **0.095 ms** | 最大误差 0.03125 |

正常自动调优仍选择 `XBLOCK=4、R0_BLOCK=5120、grid=2048`。这组实验当时证明避免常量标记可以恢复性能，但后续相同二进制对照进一步证明它只是临时规避，真正根因是 5.4 的 C launcher 参数打包。

### 5.4 后续深入定位：真正根因在 C launcher 参数打包

常量标记最初只是表层触发条件。慢快版本规范化 TTIR 的加载、归约、`rsqrt` 和存储完全相同；TTAdapter 和 BCMLIR 也只有特化标量及 program-id 编号差异。反汇编均为 580 行，没有慢版增加数千倍指令的证据。

进一步构造“保留 `r0_numel` 常量并增加运行时 dummy”和“运行时 `r0_numel`、无 divisibility 属性”两组，它们具有相同规范化 TTAdapter、相同 BCMLIR、相同 `.npubin` SHA256，但耗时分别为 686.37 ms 和 0.0897 ms。这证明同一设备二进制仍可因启动签名和参数打包不同而产生快慢差异。

最终定位到 Triton-Ascend `third_party/ascend/backend/driver.py`：`make_launcher(constants, signature, metadata)` 接收却未使用 `constants`，已从 TTIR 删除的特化参数仍作为普通 `i32` 打包，导致后续隐藏 grid 参数偏移与二进制约定不一致。

上游 `Ascend/pytorch@24c4858c` 的 static/fast launcher 修改不是本问题修复；本问题位于 Triton-Ascend C launcher 的通用参数打包。最终修复保留所有常量特化，不再限制非 2 次幂归约长度。

## 6. 修复后的验证结果

6.1～6.3 记录的是早期 Inductor“非 2 次幂不特化”临时规避的验证，用于证明性能可以恢复；该修改已撤销。最终 Triton-Ascend C launcher 修复及保留常量的验证见 6.4。

### 6.1 实际生成内核

使用全新编译缓存重新启动 Inductor 服务后，目标模板的 `triton_meta["constants"]` 已为空，原始融合结构、`XBLOCK=4`、`R0_BLOCK=5120`、`num_warps=16` 和 `grid=2048` 均保留。直接加载这份实际生成模板进行独立测试：

- 独立测试平均设备耗时 **0.0892 ms**。
- 8192 行均在误差检查范围内，两个输出的最大绝对误差均为 **0.03125**。
- 未使用命令行 pin，正常自动调优选择了上述原配置。
- 修复后 rank0 prefill trace 中，32 次同形状调用的平均耗时为 **80.54 μs**；修复前为 374222.77 μs。

### 6.2 相同 profiling 负载下的模型对照

| 指标 | default | 修复前 Inductor | 修复后 Inductor |
|---|---:|---:|---:|
| 完成 1024 tokens 的请求数 | 8/8 | 8/8 | 8/8 |
| 平均 TTFT | 14.513 s | 21.497 s | **14.514 s** |
| 最慢请求耗时 | 51.173 s | 63.365 s | **50.561 s** |
| prefill 采集窗口 | 25.966 s | 37.838 s | **25.982 s** |
| decode 采集窗口 | 4.041 s | 4.084 s | **3.926 s** |

修复后 TTFT 和端到端请求耗时已恢复到 default 同水平。随机 token 长输入下，修复后与 default 有 1/8 条完整文本一致，与修复前 Inductor 有 4/8 条一致；该负载用于性能复现，不以文本完全一致作为数值判定。数值正确性由上述逐元素算子检查确认。

本节的临时规避结果说明性能可以恢复，但不再据此将原因归为非 2 次幂常量折叠。最终原因是 5.4 所述的特化参数设备打包错误；default 与 Inductor 的图模式、冷编译、量化矩阵乘、注意力和 grid 均不是主因。

### 6.3 非 profiling 官方性能复测

使用与原始性能矩阵相同的 `vllm bench serve` 配置：16 条请求、并发 8、输入 32768 tokens、输出 1024 tokens。default 和修复前 Inductor 取原三次重复的中位数，修复后执行一次。

| 指标 | default | 修复前 Inductor | 修复后 Inductor | 修复后/修复前 |
|---|---:|---:|---:|---:|
| 输出吞吐 | 162.76 tokens/s | 131.25 tokens/s | **165.12 tokens/s** | **1.258x** |
| 请求吞吐 | 0.15895 req/s | 0.12817 req/s | **0.16125 req/s** | **1.258x** |
| 平均 TTFT | 11.185 s | 16.035 s | **11.131 s** | 时间下降 30.59% |
| 平均 TPOT | 38.140 ms | 45.210 ms | **37.490 ms** | 时间下降 17.08% |
| 平均端到端耗时 | 50.198 s | 62.284 s | **49.483 s** | 时间下降 20.55% |
| 完成请求数 | 16/16 | 16/16 | 16/16 | — |

修复后的输出吞吐为 default 的 **1.014x**，长上下文性能回退已消除。

### 6.4 最终 C launcher 修复：保留常量特化

最终 codegen 已恢复原样，真实模型模板仍包含 `'constants': {'r0_numel': 5120}`。Triton-Ascend driver 在设备打包时将 `constants` 中的顶层参数视为 `constexpr`，Python 侧仍保留完整参数个数检查和解析。

| 验证 | 平均耗时 | 数值结果 |
|---|---:|---|
| 原常量内核，固定配置，未修 launcher | 377.85 ms | 最大误差 0.03125 |
| 原常量内核，固定配置，C launcher 修复 | **0.08995 ms** | 最大误差 0.03125 |
| 原常量内核，正常自动调优，C launcher 修复 | **0.08953 ms** | 最大误差 0.03125 |
| 运行时参数路径回归，C launcher 修复 | **0.08974 ms** | 最大误差 0.03125 |

8192 行均通过检查。最终模型 profiling 的 8 条请求全部完成 1024 tokens，平均 TTFT **14.504 s**，最慢请求 **50.593 s**，prefill 窗口 **25.964 s**，均与 default 同水平。该结果不依赖取消常量特化。

最终非 profiling `vllm bench serve` 复测同样保留该常量：输出吞吐 **165.10 tokens/s**、平均 TTFT **11.133 s**、平均 TPOT **37.493 ms**、平均端到端耗时 **49.488 s**，16 条请求全部完成。结果见 `driver_fix_performance/`。

## 7. 限制

- 算子累计设备时间不能直接当成端到端耗时。
- 本报告不使用 profiling 状态下的客户端吞吐作为原性能基准；原基准以三次非 profiling `vllm bench serve` 结果为准。
- 根因已定位到 C launcher 的特化参数打包；合入前仍需覆盖多个特化标量、混合常量/运行时参数及普通 kernel 的通用回归。
