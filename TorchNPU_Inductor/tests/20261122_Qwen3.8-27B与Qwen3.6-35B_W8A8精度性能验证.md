## 4. 35B 启动问题与 vLLM Ascend 修复

### 4.1 初始现象

35B 的 eager 任务集和固定输入测试最初均在初始化阶段失败。监控进程发现 `WorkerProc hit an exception` 后提前终止，首次日志没有保留完整异常栈。随后直接运行 eager 复现，得到实际错误：

```text
call aclnnGroupedMatmulSwigluQuantWeightNZ failed
Config_Error(EZ1013)
In the dynamic shape scenario, the JSON configuration file of operator
aclnnGroupedMatmulSwigluQuantWeightNZ_1692_GroupedMatmulSwigluQuant
cannot be found.
```

该问题发生在 eager 和 Inductor 共用的 CANN MoE 算子，不是 Inductor 编译特有问题。

### 4.2 原因与修改

当前 CANN 安装中存在 `GroupedMatmulSwigluQuantV2` 的动态 shape 配置，而 W8A8 分支仍直接调用旧版 NZ 接口。

本地和服务器均修改：

`inductor-meta-worktree/vllm-ascend/vllm_ascend/quantization/methods/w8a8/w8a8_dynamic.py`

将普通融合分支从：

```python
torch.ops._C_ascend.grouped_matmul_swiglu_quant_weight_nz(...)
```

改为：

```python
torch_npu.npu_grouped_matmul_swiglu_quant_v2(...)
```

具体调整：

- 权重和 scale 按 V2 接口要求使用列表；
- 保留融合计算，没有关闭融合特性；
- 删除 V2 schema 不支持的 `swiglu_limit` 参数。该模型使用普通 SwiGLU，本次路径不依赖此参数。

在现有 `tests/ut/quantization/methods/w8a8/test_w8a8_dynamic.py` 中新增接口测试，检查 V2 调用、权重列表及参数集合。

### 4.3 修复验证

- 新增 V2 接口单元测试：1 项通过；
- 35B eager 真实生成成功，进程退出码为 0；
- 修复后 eager/Inductor 固定输入、任务集和两轮性能矩阵均执行完成；
- 原测试文件共运行 13 项，其中本次新增测试和其余 10 项通过；另外 2 个 MegaMoe 用例在 CPU 下因 `npu_format_cast` 不支持而失败。这两个失败与本次 V2 调用修改无关，本任务未修改它们。

本次没有修改 CANN 或 Triton-Ascend，也没有将之前的 sigmoid 精度原型带入测试。

## 8. 为什么 Inductor 没有带来成倍的性能优势

### 8.1 default 已经是编译和融合路径

default 不是逐算子执行的 eager。AscendCompiler 本身会进行编译和融合，并且关键路径已经调用 CANN 的高性能融合算子。Inductor 所替换的是另一条成熟编译路径，而不是在未优化的 eager 上做优化。

两条路径本次均使用 `FULL_AND_PIECEWISE`，因此也不是只有 Inductor 使用了图回放。

### 8.2 主要耗时算子没有被替换

27B 之前的 profiling 已直接显示，default 与 Inductor 中主要 CANN 算子的设备耗时基本一致：

| 算子 | Inductor/default 设备耗时比 |
|---|---:|
| QuantBatchMatmulV3 | 0.999 |
| FusedInferAttentionScore | 0.997 |
| ChunkGatedDeltaRuleFwdH | 1.000 |

详见 `20261119_Qwen3.8-27B-w8a8_32768_1024_profiling.md`。

Inductor 主要融合周边的 add、RMSNorm、dynamic quant、类型转换和部分逐元素或归约计算。这些融合确实存在，但它们不是全部模型耗时，且 default 已经拥有 `AddRmsNormDynamicQuantV2`、`RmsNorm` 等 CANN 实现。Triton 生成内核也不必然超过针对硬件优化的 CANN 内核。

因此可以用下式理解端到端收益：

```text
总耗时 = 主要 CANN 算子 + 通信与调度 + 周边计算
```

Inductor 主要影响最后一部分，而 default 对这部分也已有优化。

本轮没有重新 profiling 35B，所以上述逐项算子证据直接对应 27B；35B 的具体耗时构成仍需通过 profiling 单独确认。

### 8.3 负载本身限制部分指标

- QPS 1：请求到达速率限制了吞吐，两边均约为 252 tokens/s，应更多观察 TTFT 和 TPOT；
- 32K 长输入：prefill 主要由量化矩阵乘和注意力决定，这些 CANN 算子没有变化；
- 无限并发：吞吐受计算、显存带宽和通信限制，周边融合的增量收益有限。

任务集运行时长受 AISBench 调度、输出长度和异常检查影响，不应代替正式性能测试解释。

## 9. 27B 既有 RMSNorm 性能问题是否复现

### 9.1 端到端结果没有复现

`20261119_Qwen3.8-27B-w8a8_32768_1024_profiling.md` 中，原问题在 32K/1024 下表现为：

- 输出吞吐从 default 的 162.76 降至 131.25 tokens/s，下降约 19.4%；
- 平均 TTFT 从 11.185 秒增至 16.035 秒，增加约 43%；
- 目标融合内核在 8192×5120 prefill 形状下平均耗时约 374 ms。

本次 27B 的两轮 32K/1024 结果：

| 指标 | 第 1 轮 Inductor/default | 第 2 轮 |
|---|---:|---:|
| 输出吞吐比 | 0.986 | 0.986 |
| 平均 TTFT 比 | 1.003 | 1.030 |
| 平均 TPOT 比 | 1.018 | 1.010 |

没有复现原来的明显性能回退。

### 9.2 编译缓存说明这次没有进入原触发路径

直接检查本次 27B Inductor 缓存，目标内核仍存在：

```text
triton_unk_fused_add_npu_dynamic_quant_npu_rms_norm_0
```

但 rank0 和 rank1 的生成结果均为：

```python
'signature': {
    # ...
    'r0_numel': 'i32'
},
'constants': {}
```

调用处将 5120 作为运行时参数传入：

```python
kernel.run(..., r0_numel, 5120, stream=...)
```

原文问题版本则包含：

```python
'constants': {'r0_numel': 5120}
```

原问题涉及常量特化后设备参数与 launcher 打包约定不一致。本次 `r0_numel` 没有被标记为常量，因此没有进入该触发路径。

同时，当前服务器的 `triton-ascend/third_party/ascend/backend/driver.py` 中，`make_launcher(constants, ...)` 仍只是接收 `constants`，没有包含文档末尾所述的最终参数打包修复。

所以本次结果只能说明：

- 使用运行时 `r0_numel` 的编译结果性能正常；
- 没有复现原问题；
- **不能据此证明最终 C launcher 修复已在当前环境生效。**

若要验证最终修复，需要应用 launcher 修改、清除对应 Inductor 缓存重新编译，确认生成结果恢复 `'constants': {'r0_numel': 5120}`，再运行 32K 数值和性能验证。本任务没有进行这项额外修改。
