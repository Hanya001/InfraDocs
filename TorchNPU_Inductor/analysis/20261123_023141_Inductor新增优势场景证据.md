# Inductor 新增优势场景：性能、Profile 与静态代码证据

日期：2026-11-23。环境：A5-25，Ascend950DT，torch 2.13 / vLLM 0.33。

本文是独立的新增分析，不修改此前的 8B-W8A8、27B-W8A8、30B-A3B-W8A8 报告。三个新场景为 **Qwen3.8-27B BF16、Qwen3.6-35B-A3B-W8A8、Qwen3.5-0.8B**。Qwen2.5-VL 的首轮高收益经复测未成立，作为反证保留。

## 1. 结论摘要

| 场景 | 原始端到端收益 | Profile 能证明的直接机制 | 不能据此宣称的内容 |
|---|---|---|---|
| 27B BF16，ShareGPT QPS4 | 吞吐 **+8.43%**，TPOT **-9.02%**，TTFT **-36.66%** | Stage/步 **-7.28%**，Free/步 **-46.12%**；Slice、TensorMove 和部分融合开销下降 | Computing/步反而 **+3.44%**；不是 GEMM/Attention 普遍提速 |
| 35B-A3B-W8A8，ShareGPT QPS16 | 两轮吞吐 **+8.57%/+5.10%**，TPOT **-7.81%/-4.77%** | 小算子和数据移动确实减少；固定 decode 的 Host launch 时间下降 | 固定形状 Computing 没下降；ShareGPT 窗口的大算子降时不能当作同 shape kernel 加速 |
| Qwen3.5-0.8B，ShareGPT QPS16 | 两轮吞吐 **+15.38%/+8.34%**，TPOT **-15.09%/-8.66%**，TTFT **-45.19%/-32.50%** | 两轮均消除绝大多数 `>50 ms` 长间隔，最大并发下降；图层小算子融合存在 | 新 Profile 的 Stage/Computing 反而增加；不是单步计算加速，8K decode 明确回退 |

这三组结果支持一个更谨慎的结论：**Inductor 可以稳定减少部分 elementwise/layout 工作，并在特定模型和负载下改善执行间隙或尾延迟；端到端大幅收益往往还包含请求组成、等待和积压变化。** 本文不会把设备 Free、HCCL Wait 或请求排队下降写成计算 kernel 的同幅度加速。

所有场景都只有性能证据，不构成精度优势；原矩阵中这些模型的固定输入 logprob 均未通过既有容差。

## 2. 数据与计算口径

- 最终收益使用未开启 Profiler 的原始 `vllm bench serve` JSON；Profile 用于解释机制，不用其受扰动的吞吐替代原始结果。
- Default 为 `AscendCompiler`，Inductor 为 `backend=inductor` / `triton_experimental`；两条路径均为 O2、`FULL_AND_PIECEWISE`，模型、TP、seed 和负载参数一致。
- ShareGPT 每组 200 条请求均成功，Default/Inductor 的逐请求输入长度完全一致，输出均为 256 tokens。VL 8K 为 32 条请求，输入均为 8192、输出均为 1024，最大并发固定为 8。
- ShareGPT/VL 的第 5 秒窗口缺少 TASK 数据，报告使用第 30 秒的第二个完整窗口。35B 固定 decode 使用独立的第二个窗口。
- 不同窗口的引擎步数不同，因此所有 Stage、Computing、Free、Communication、算子和 Host launch 都按实际步数归一化。按步归一化不能消除 batch、prefill/decode 比例和 shape 差异。
- `Computing` 是设备计算时间，`Free` 是设备执行间隙；Host API 累计时间不能再与二者相加。TP2 的两张卡分别分析，不把两卡 Stage 相加。
- 原始归档、SHA256 和重算结果见 [raw_analysis.json](../../../../profilling/20261123_023141_inductor_new_scenarios_evidence/20261123_023141_raw_analysis.json)；Profile 归一化结果见 [derived_profile_metrics.json](../../../../profilling/20261123_023141_inductor_new_scenarios_evidence/20261123_023141_derived_profile_metrics.json)。两者都可由同目录脚本重新生成。

## 3. 场景一：Qwen3.8-27B BF16——直接收益主要来自设备间隙减少

### 3.1 原始收益及排队成分

| ShareGPT 负载 | 输出吞吐：D → I | 平均 TPOT：D → I | 平均 TTFT：D → I |
|---|---:|---:|---:|
| QPS1 | 248.843 → 248.911，+0.03% | 23.901 → 23.418 ms，-2.02% | 140.889 → 121.791 ms，-13.56% |
| QPS4 | 751.690 → 815.024，**+8.43%** | 36.784 → 33.468 ms，**-9.02%** | 4950.769 → 3135.759 ms，**-36.66%** |
| QPS16 | 781.672 → 829.415，+6.11% | 36.462 → 34.531 ms，-5.30% | 21244.946 → 19483.918 ms，-8.29% |

QPS4 最大并发请求数从 71 降至 56。按请求顺序每 50 条分段，平均 TTFT 为：

| 路径 | 1～50 | 51～100 | 101～150 | 151～200 |
|---|---:|---:|---:|---:|
| Default | 214.036 | 3746.970 | 6890.890 | 8951.181 ms |
| Inductor | 160.161 | 3078.060 | 4776.692 | 4528.124 ms |

首段已下降 25.17%，末段下降 49.41%。因此 QPS4 同时具有直接执行改善和积压缓解，不能把所有 TTFT 收益归于 prefill kernel。

### 3.2 第二个 Profile 窗口：Stage 降 7.28%，但 Computing 没降

窗口实际为 Default 45 步、Inductor 49 步。每步数据：

| 指标 | Default | Inductor | I 相对 D |
|---|---:|---:|---:|
| Stage | 45158.256 μs | 41870.684 μs | **-7.28%** |
| Computing | 35390.373 μs | 36607.431 μs | **+3.44%** |
| Free | 9767.879 μs | 5263.250 μs | **-46.12%** |
| 算子数 | 1581.467 | 1560.592 | -1.32% |
| Host launch 次数 | 377.289 | 318.776 | **-15.51%** |
| Host launch 时间 | 1396.598 μs | 1282.738 μs | -8.15% |

每步 Free 减少 4504.629 μs，覆盖 Computing 增加的 1217.058 μs 后，Stage 净减少 3287.572 μs。这与原始 QPS4 TPOT 约 9% 的下降方向一致，说明该场景的直接收益主要是**提交/调度路径和设备间隙缩短**，不是设备计算整体变快。

`launch` 是汇总节点口径；底层 `aclrtLaunchKernelWithHostArgs` 每步次数和时间分别增加 1.15% 和 4.50%。所以应表述为“汇总 launch 节点减少”，不能扩展成所有 ACL 调用都减少。

### 3.3 算子和静态代码：哪些优化真实存在

| 路径 | 每步总时间：D → I | 变化 |
|---|---:|---:|
| Slice + 新增 clone/split | 1224.096 → 956.731 μs | **-21.84%** |
| TensorMove | 90.942 → 54.290 μs | **-40.30%** |
| Sigmoid + Mul → 单个融合 kernel | 144.334 → 106.902 μs | **-25.93%** |
| Add → 新增 add kernel | 356.849 → 270.708 μs | **-24.14%** |
| 原生 RmsNorm → Triton RMSNorm | 6.820 → 54.907 μs | **回退** |
| MatMulV3 | 24661.555 → 25687.120 μs | **+4.16%** |
| FusedInferAttentionScore | 789.707 → 806.791 μs | +2.16% |

生成代码证明 `triton_unk_fused_mul_sigmoid_view_0` 的来源节点是 `view/sigmoid/mul`，kernel 内两次 load 后执行 sigmoid、乘法并一次 store：`20261123_023141_static_code/qwen38_27b_bf16/000_inductor_cache_3z_c3ztfqakrbzusnj66kcdd2bxtfe2k2xjizby6brep4vkqocpxshb.debug.py` 第 42～53、93～97 行。

RMSNorm 的 FP32 转换、平方、均值、rsqrt、权重加一和输出转换也确在一个 kernel 内；但输入被读取两遍，且 Profile 显示其本窗口更慢。`triton_unk_fused_add_npu_add_rms_norm_1` 名称容易造成误解：其实只计算 `weight + 1`，真正的 AddRmsNorm 仍由原生算子执行。

**最终归因：**小算子融合和 Slice/TensorMove 减少是真实的，但它们没有带来 Computing 净下降；该场景最有说服力的直接收益是 Free 和 Host 路径改善。

## 4. 场景二：35B-A3B-W8A8——两轮高负载收益，主要是长尾和等待改善

### 4.1 两轮结果都可复现正向收益

| ShareGPT QPS16 | 输出吞吐：D → I | 平均 TPOT：D → I | 平均 TTFT：D → I |
|---|---:|---:|---:|
| 第1轮 | 1174.530 → 1275.137，**+8.57%** | 24.557 → 22.640 ms，-7.81% | 12748.713 → 11211.235 ms，-12.06% |
| 第2轮 | 1211.021 → 1272.732，**+5.10%** | 23.802 → 22.668 ms，-4.77% | 12153.986 → 11282.208 ms，-7.17% |

两轮均为 200/200 成功，输入均为 45983 tokens，输出均为 51200 tokens。最大并发数几乎不变（168→166、168→167），说明收益不是简单降低客户端并发上限得到的。

中位 ITL 两轮仅下降 0.32%/0.15%，而 p95/p99 ITL：

- 第1轮：126.661→101.063 ms、179.682→150.747 ms；
- 第2轮：115.548→101.333 ms、172.473→150.276 ms。

因此原始收益主要体现在**长尾间隔和积压持续时间缩短**，而不是普通 decode token 间隔普遍下降 5%～8%。

### 4.2 ShareGPT Profile 有改善，但工作组成不同

第二个窗口中 Default 两 rank 均 27 步，Inductor 均 104 步。每步 Computing 分别下降 19.03%/19.42%，算子数下降 11.90%，汇总 Host launch 次数下降 88.61%。但 rank0 Communication/步下降 90.59%，rank1 Free/步下降 91.99%，表明两窗口还包含明显不同的等待与调度状态。

Default rank0 的原始 Communication 汇总中 Wait 为 3027.865 ms，而 Transit 只有 82.859 ms；两条路径每步仍是 81 次 allReduce + 1 次 allGather。因此 Communication 大降主要包含等待减少，不是通信链路加速 90%。

同样，ShareGPT 窗口里 MoE/GEMM/Attention 的步均时间下降混合了 shape、batch 和 prefill/decode 组成差异。为避免错误归因，追加固定 token ID、8 请求、输入 256 tokens 的 decode 64～128 实验。

### 4.3 固定形状 decode 排除了“大 GEMM 普遍提速”

Default 捕获 65 步、Inductor 64 步；主要算子每步次数相同。以下为每步变化：

| 指标 | rank0 | rank1 |
|---|---:|---:|
| Stage | -0.80% | **+0.37%** |
| Computing | **+1.06%** | **+0.62%** |
| Free | -22.72% | -5.97% |
| Host launch 时间 | **-16.91%** | **-6.80%** |
| GroupedMatmulSwigluQuantV2，40次/步 | **+1.75%** | **+1.21%** |
| GroupedMatmul，40次/步 | **+2.70%** | **+2.84%** |
| MatMulV3，261次/步 | +0.25% | +0.29% |
| FusedInferAttentionScore，10次/步 | -0.23% | -0.13% |

ShareGPT 窗口中这些大算子的显著降时在固定形状下消失或反转。报告因此不保留“大 GEMM/Attention 被 Inductor 明显加速”的解释。

固定形状仍真实存在的变化：

- Slice：220→120 次/步，时间下降 38.15%/37.25%；
- Add：101→0 次/步；ZerosLike：31→1 次/步；Index：13→3 次/步；
- 新增 11 类 Triton kernel，共 241 次/步；同时 Cast 时间增加 43.99%/38.43%；
- Computing 没下降，rank0 的 Stage 小幅收益主要来自 Free/Communication，rank1 总体略回退。

**最终归因：**两轮原始 QPS16 收益是可靠的系统结果；小算子/layout 减少和 Host 时间下降是其可信的局部机制，尾延迟分布证明最终改善以长尾和等待为主。固定 decode 反证限制了直接计算归因，不能把 ShareGPT 窗口的 19% Computing 降幅当作同 shape 的普遍能力。

## 5. 场景三：Qwen3.5-0.8B——两轮高负载收益来自长尾消除，而非单步提速

### 5.1 两轮非 Profile 结果均为正

| ShareGPT QPS16 | 输出吞吐：D → I | 平均 TPOT：D → I | 平均 TTFT：D → I |
|---|---:|---:|---:|
| 第1轮 | 2796.152 → 3226.184，**+15.38%** | 10.037 → 8.523 ms，**-15.09%** | 1954.346 → 1071.268 ms，**-45.19%** |
| 第2轮复测 | 2904.244 → 3146.400，**+8.34%** | 9.686 → 8.847 ms，**-8.66%** | 1895.831 → 1279.774 ms，**-32.50%** |

两轮均为 200/200 成功，输入均为 45983 tokens，输出均为 51200 tokens。最大并发请求数第一轮 87→72，第二轮 85→74。两条路径的请求吞吐都低于 16 req/s 到达率，存在持续积压；Inductor 更快完成请求，并发峰值和首 token 前等待随之下降。

第一轮按请求顺序每 50 条分段，平均 TTFT 为：

| 路径 | 1～50 | 51～100 | 101～150 | 151～200 |
|---|---:|---:|---:|---:|
| Default | 126.120 | 1311.096 | 2719.211 | 3660.955 ms |
| Inductor | 91.950 | 974.370 | 1565.926 | 1652.825 ms |

后段改善大于首段，与积压逐步缩短一致。因此 TTFT 收益主要是系统排队结果，不是 prefill kernel 直接加速 45%。

### 5.2 最有说服力的证据：少量长停顿主导平均 TPOT

| 轮次与路径 | 中位 ITL | P95 ITL | P99 ITL | `>50 ms` 数量 | `>50 ms` 累计 |
|---|---:|---:|---:|---:|---:|
| 第1轮 Default | 5.226 | 51.645 | 68.718 ms | 3272 / 51000 | 200.368 s |
| 第1轮 Inductor | 5.351 | 37.442 | 39.306 ms | **0 / 51000** | **0 s** |
| 第2轮 Default | 5.425 | 49.022 | 50.167 ms | 837 / 51000 | 42.401 s |
| 第2轮 Inductor | 5.490 | 39.646 | 40.933 ms | **14 / 51000** | **0.787 s** |

两轮中位 ITL 都略退化（+2.38%/+1.20%），但 P95/P99 和 `>50 ms` 长停顿显著下降。这与“普通 token 计算没有普遍变快，长尾调度停顿减少”完全一致。

对第一轮 51000 个间隔做算术分解：

```text
>50 ms 部分对均值的贡献下降    200.368 s / 51000 = 3.928775 ms
≤50 ms 部分对均值的贡献上升    (434.663-311.528) s / 51000 = 2.414395 ms
净下降                       3.928775-2.414395 = 1.514380 ms
原始平均 TPOT 下降             10.037176-8.522796 = 1.514380 ms
```

第二轮同样闭合：长尾贡献减少约 0.815950 ms，普通间隔贡献也减少约 0.022914 ms，净下降 0.838864 ms，等于 9.685969-8.847105 ms。**平均 TPOT 收益由长尾消除解释，而不是由中位 decode 间隔改善解释。**

### 5.3 Profile 反证：单步执行没有变快

第二个完整窗口为 Default 173 步、Inductor 171 步：

| 指标/步 | Default | Inductor | 变化 |
|---|---:|---:|---:|
| Stage | 11674.066 μs | 11939.477 μs | **+2.27%，回退** |
| Computing | 3939.224 μs | 4093.428 μs | **+3.91%，回退** |
| Free | 7734.843 μs | 7846.049 μs | +1.44% |
| 算子数 | 642.249 | 652.912 | +1.66% |
| Host launch 次数 | 106.249 | 106.953 | +0.66% |
| Host launch 时间 | 397.005 μs | 403.680 μs | +1.68% |

底层 `aclrtLaunchKernelWithHostArgs` 每步次数和时间还分别增加 16.62%/15.04%。因此不能将这个场景写成单步执行或 Host launch 加速。

图层优化本身确实存在：Slice 次数/步下降 43.43%，Add、Sigmoid、Mul、原生 RmsNorm 消失，ZerosLike 次数下降 94.62%；生成代码也证明 RMSNorm 和 `view+sigmoid+mul` 融合。但新增 11 类 Triton kernel 每步消耗 433.631 μs，Cast 时间增加约 406%，MatMulV3 和 Attention 每步时间分别增加 2.71%/2.51%，最终 Computing 没有净收益。

**最终归因：**两轮端到端收益真实且可复算，证据指向持续负载下的长尾停顿和积压减少；Profile 明确否定了“单步计算更快”的解释。这个案例的价值是证明 Inductor 可以在普通间隔略慢的情况下，通过改善尾部分布获得系统收益，而不是证明所有 kernel 都得到优化。

### 5.4 适用边界

QPS1 TPOT 回退约 5.05%，QPS4 TPOT 回退约 1.38%；随机 8192/1024 的吞吐从 1933.781 降至 1624.386 tokens/s（-16.00%），TPOT 增加 20.97%。因此本场景只支持 **ShareGPT 类短输入、高请求速率** 的系统收益，不能外推到低负载或 8K 长上下文 decode。当前也没有 8K Profile，不能猜测其回退原因。

## 6. 被复测排除的 VL 场景与总体边界

Qwen2.5-VL 的首轮 8K 结果曾显示吞吐 +52.96%，但第二轮非 Profile 复测为 Default 736.965、Inductor 711.509 tokens/s，Inductor 反而 **-3.45%**，TPOT/TTFT 也回退。Default 首轮到第二轮从 465.070 升至 736.965，而 Inductor 从 711.370 到 711.509 很稳定，说明首轮主要是 Default 异常慢。VL 因此不作为优势场景；其 Profile 中 Slice/ViewCopy 减少的局部现象仍保留在证据目录，但不能用来支持 52.96% 的优势结论。

综合三个主场景：

1. **最稳定的图层变化**是 RMSNorm、sigmoid+mul、split/clone/copy 等小算子融合和寻址折叠。
2. **直接收益与系统收益必须分开**：27B BF16 有 Stage/Free 直接改善；35B 和 0.8B 的端到端收益主要表现为高负载长尾与等待减少。
3. **共同反证**是新增 Triton 不一定比原生 kernel 更快，Cast 等新增开销可能抵消收益，大 GEMM/Attention/MoE 没有普遍加速证据。
4. 单个短 Profile 窗口不是端到端收益的充分证明；首轮高收益也必须复测。只有原始逐请求数据、Profile/同形状补充实验和生成代码共同支持时，才给出因果结论。
