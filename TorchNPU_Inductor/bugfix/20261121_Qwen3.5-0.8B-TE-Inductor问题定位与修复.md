# Qwen3.5-0.8B：TE Inductor 初始化失败与异常输出定位

## 1. 当前结论

Qwen3.5-0.8B 在当前 torch 2.13 / vLLM 0.33 环境中运行 TE Inductor 时，依次暴露了三个问题：

1. TE linearize 后处理把间接索引的 `tmp0 < 0` 错写为 `tmp0 < 2`。
2. int64→int32 downcast 缓存读取 inference tensor 的 `_version`，导致所有 tiling 被判定为不可运行。
3. 修复初始化后，用户自定义 Triton LayerNorm 的 lowering 和 FP32 参数处理问题导致模型连续输出 `!`。

三个问题分别修复后，Qwen3.5-0.8B 的冷编译、无插桩缓存复跑和最终复验均通过，chat 输出正常。当前修改尚未提交或推送。

之前同一模型能够运行，是因为之前的 torch 2.14 环境走 ATen index fallback，不进入前两个问题的 TE index kernel 路径，并且已经包含第三个问题的修复。

追踪表关联项：F-05、R-01、R-04。

## 2. 环境与问题现象

环境：

- a5-25，Ascend950DT，CANN 9.2.0；
- torch 2.13.0+cpu；
- torch_npu 2.13.0.post1+git6efa6d0；
- triton-ascend 3.6.0.post2；
- vLLM 0.33.0；
- Qwen3.5-0.8B，BF16，单卡。

Inductor 配置：

```python
compilation_config={"backend": "inductor"}
```

同时设置：

```bash
VLLM_USE_BREAKABLE_CUDAGRAPH=0
```

避免 breakable CUDA graph 配置让 Inductor 路径失效。

### 2.1 初始现象：EngineCore 初始化失败

失败发生在 profile run：

```text
RuntimeError: All tiling for [triton_unk_fused_index_2] are not runnable.
```

这个信息只是上层汇总，不能直接证明所有 tiling 都存在编译错误。后续拿到的真实 PreRun 异常是 inference tensor 的 `_version` 错误。

### 2.2 修复 index 后：仍然在初始化阶段失败

将生成代码中的比较常量恢复为 `0` 后，完整模型仍在同一 index kernel 上失败。说明除了生成代码错误，还有运行时 downcast 问题。

### 2.3 修复初始化后：连续输出 `!`

修复前两个问题后，模型能够初始化和生成，但三个请求都输出 512 个 `!`。

原验证脚本只检查输出非空，因此一度误报 PASS。后续加入有效字符断言，将全标点输出判为失败，避免把“进程正常退出”当作“模型结果正确”。

## 3. 定位过程

### 3.1 提取失败的生成 kernel

从 vLLM 编译缓存中取出 `triton_unk_fused_index_2` 所在的 `output_code.py`。该 kernel 对 RoPE 的 `cos_sin_cache` 做间接索引，关键代码为：

```python
tmp2 = tmp0 + 262144
tmp3 = npu_triton_helpers.lt(tmp0, 2)
tmp4 = tl.where(tmp3, tmp2, tmp0)
```

`aten.index` 的负索引包装本应只在 `tmp0 < 0` 时加上索引表大小。写成 `< 2` 后，合法索引 0 和 1 也会被错误地加上 262144。

### 3.2 拆出 kernel，与 eager 对比

将失败的 kernel 从完整模型中拆出，构造相同形状和动态参数：

- 使用大于等于 2 的随机合法索引时，kernel 可以运行；
- 使用全 0 索引时，输出与 eager 相比 3072/3072 个元素全部不一致。

这证明生成代码存在独立的语义错误，不只是 autotune 配置问题。

### 3.3 追踪 `< 0` 在哪里变成 `< 2`

在 `NPUTritonKernelOverrides.lt()` 入口临时打印参数：

```text
TRACE_LT>>> NPUTritonCSEVariable('tmp0') 0
```

入口收到的是正确的 `0`，最终文件却变成 `2`。因此错误发生在代码生成后的 linearize 后处理，而不是上游 `aten.index` lowering 最初传错常量。

### 3.4 获取完整模型中每种 tiling 的真实异常

普通 vLLM DEBUG 配置不会输出 torch_npu 的 PreRun 日志，因此给验证脚本临时加入：

- torch_npu autotune logger 的 DEBUG handler；
- `NPUCachingAutotuner.run` 包装，打印索引 shape、stride 和范围。

模型实际输入：

```text
shape   = (3, 16384)
stride  = (16385, 1)
ks0/ks1 = (16385, 16384)
min/max = 0 / 1023
```

索引完全合法。三种 tiling 的真实异常均为：

```text
Inference tensors do not track version counter.
```

所以“所有 tiling 不可运行”只是上层汇总，底层不是 NPU 编译失败。

### 3.5 构造 inference downcast 最小复现

直接调用：

```python
with torch.inference_mode():
    x = torch.randint(0, 1024, (3, 16), device="npu", dtype=torch.int64)

y = _memoized_downcast(x, torch.int32)
```

稳定复现：

```text
ver = src._version
RuntimeError: Inference tensors do not track version counter.
```

### 3.6 用 default 后端检查用户 Triton kernel

在前两个问题修复后，使用 default NPU 后端做对照，暴露：

```text
_layer_norm_fwd_1pass_kernel_npu
operator 'sqrt' does not support dtype 'float64'
```

由此定位到用户自定义 Triton kernel 的参数签名和 lowering。已有的 `3c5c3eb375 fix(inductor): preserve user-defined Triton kernels` 提交正好覆盖这两个问题，其历史验证也包含 Qwen3.5 连续输出 `!` 的现象。

## 4. 三个根因与修复方法

### 4.1 根因一：reduction 后处理误改 TE helper 参数

位置：

`torch_npu/_inductor/triton_experimental/codegen/triton.py`，`_apply_linearize()`。

该逻辑原本要把 reduction 调用的旧维度编号替换为 linearize 后的新维度编号：

```python
line.replace(f", {old_reduction_dim})", f", {real_reduction_dim})")
```

匹配条件包含：

```python
"triton_helpers."
```

但 `npu_triton_helpers.` 也包含这个子串，因此普通 TE 比较 helper 同样进入替换。对于从原始一维变为三维的 index kernel：

```text
old_reduction_dim = 0
real_reduction_dim = 2
```

最终就把：

```python
npu_triton_helpers.lt(tmp0, 0)
```

错误改成：

```python
npu_triton_helpers.lt(tmp0, 2)
```

修复方式是在该替换条件中排除 `npu_triton_helpers.*`：

```python
and "npu_triton_helpers." not in line
```

同时保留对上游 `triton_helpers.max2/min2` 等 reduction 调用的原处理。不能只排除 `lt`，因为同一替换也可能误改 `gt/le/ge` 等其他 TE helper。

### 4.2 根因二：downcast 缓存不支持 inference tensor

位置：

`torch_npu/_inductor/triton_experimental/npu_triton_heuristics.py`，`_memoized_downcast()`。

原实现通过 `_version` 判断缓存是否有效：

```python
try:
    ver = src._version
except AttributeError:
    return _to_dtype_preserving_layout(src, dst_dtype)
```

inference tensor 不跟踪版本计数，读取 `_version` 抛出的是 `RuntimeError`，不是 `AttributeError`。异常进入 PreRun 后，所有 tiling 都被标记为失败。

修复方式：

```python
if src.is_inference():
    return _to_dtype_preserving_layout(src, dst_dtype)
```

inference tensor 不进入依赖版本计数的缓存，直接完成 dtype 转换。

历史分支 `inductor-for-vllm@2cb1a3497f` 曾采用 `(AttributeError, RuntimeError)` 的异常捕获，本次工作区使用显式 `is_inference()` 判断，两者都是退回无缓存转换。

### 4.3 根因三：用户 Triton LayerNorm 被删除及 `eps` 类型错误

这里有两个相关问题。

#### mutation HOP 被通用 fallback 覆盖

GDN 后置 LayerNorm 通过 `triton_kernel_wrapper_mutation` 调用用户 Triton kernel。TE 的批量 fallback 注册覆盖了上游专用 lowering，通用 `FallbackKernel` 又没有登记 `Y/Rstd` 的 mutation。

该 HOP 返回 `None`，于是被当成无输出、无副作用节点清理。后续 GEMM 读取未初始化 buffer，最终产生固定错误 token。

修复位置：

`torch_npu/_inductor/triton_experimental/lowering_override_list.py`

将 `_tkw.triton_kernel_wrapper_mutation` 加入 `KEEP_UPSTREAM_LOWERING`，恢复上游 `UserDefinedTritonKernel` 路径。

#### Python float 被包装为 FP64

eager Triton-JIT 将 Python float 作为 FP32 参数，而 Inductor wrapper 将该参数推导为 FP64。Triton-Ascend 当前路径不支持 FP64 `sqrt`，因此出现编译错误。

修复位置：

`torch_npu/_inductor/triton_experimental/codegen/wrapper.py`

仅在生成用户自定义 Triton kernel wrapper 时设置：

```python
with config.patch("_use_fp64_for_unbacked_floats", False):
    return super().define_user_defined_triton_kernel(*args, **kwargs)
```

这样 `eps` 与 eager 一样使用 FP32；普通 Inductor 生成 kernel 仍保留上游 FP64 精度策略。vllm-ascend 的 LayerNorm 不需要改成 `tl.constexpr`。

## 5. 引入位置与以前未触发的原因

### 5.1 前两个缺陷的引入位置

两个缺陷都随 TE 后端初始实现合入：

- 提交：[`8bfbb9ed1a`](https://gitcode.com/Ascend/pytorch/commit/8bfbb9ed1ad6157ad52d0352650dd8b7e0a9504e)
- 时间：2026-07-23
- 标题：`feat(inductor): add physically-isolated triton_experimental backend`
- MR：`Ascend/pytorch!42260`

缺陷代码较早存在，但需要相应的 index 路径才会触发。

### 5.2 当前模型开始走 TE index kernel 的位置

2026-11-11 的 [`a94d4eb291`](https://gitcode.com/Ascend/pytorch/commit/a94d4eb2917ee901a26a467533db075311d22c80) 修改了 index lowering 选择：

- 标题：`fix: prefer the upstream triton index lowering over the aclnn extern fallback`；
- MR：`Ascend/pytorch!48376`；
- 对单个张量索引且索引位于第 0 维的情况，改用上游 Inductor lowering，生成可融合的 Triton indirect-load kernel。

Qwen3.5 的 RoPE 位置索引正好满足该条件，因此当前源码会生成 `triton_unk_fused_index_*`，进入前两个问题的路径。

### 5.3 之前可用环境的实际路径

a5-28 的 torch 2.14 已验证环境中没有上述 `a94d4eb291` 路径，生成代码直接调用 ATen：

```python
buf20 = torch.ops.aten.index.Tensor(arg14_1, [arg15_1])
```

因此之前没有生成 TE index kernel，也没有进入 int64 index downcast 路径。该环境同时已经包含用户 Triton kernel 的 HOP 和 FP32 签名修复，所以连续 `!` 问题也没有出现。

时间关系：

- 2026-07-23：前两个潜在问题随 TE 初始实现引入；
- 2026-11-11：`a94d4eb291` 改变 index lowering，使当前模型开始触发它们；
- 当前 2.13 基线最初又缺少用户 Triton kernel 修复，因此在前两个问题修复后继续暴露异常输出。

## 6. 最终修改

| 文件 | 修改 |
|---|---|
| `torch_npu/_inductor/triton_experimental/codegen/triton.py` | reduction 维度替换排除 `npu_triton_helpers.*` |
| `torch_npu/_inductor/triton_experimental/npu_triton_heuristics.py` | inference tensor 绕过 downcast 缓存 |
| `torch_npu/_inductor/triton_experimental/lowering_override_list.py` | 保留 `triton_kernel_wrapper_mutation` 专用 lowering |
| `torch_npu/_inductor/triton_experimental/codegen/wrapper.py` | 用户 Triton kernel 的 Python float 使用 FP32 |

四个文件目前均为本地未提交修改，已同步到 a5-25 容器的源码树和安装副本。

## 7. 验证结果

### 7.1 最小复现

- index kernel 修复前：全 0 索引输出与 eager 全部不一致；修复后一致。
- 原始三维 index kernel：`s18=16384`、全 0 索引通过。
- inference downcast 修复前：稳定抛出 `_version` RuntimeError；修复后结果与 `x.to(torch.int32)` 一致。

### 7.2 修复范围对照

- 只保留用户 Triton kernel 修复、撤掉 index 和 inference downcast 修复时，仍在 `triton_unk_fused_index_3` 初始化阶段失败。因此 inference downcast 是消除当前初始化崩溃的必要修复。
- 保留 inference downcast 和用户 Triton kernel 修复、仅撤掉 index 修复时，完整模型可以初始化并生成，三个回答均非空且无连续 `!`。因此 index 修改不是启动和基本生成的必要条件。
- 但该对照生成的 index kernel 仍为 `npu_triton_helpers.lt(tmp0, 2)`，且长城回答与完整修复版本不同。它能运行不代表索引语义正确；第一个修改仍应作为独立的正确性修复保留，不能因“第二+第三能跑”而认定它无效或多余。

对照日志：[仅撤掉 index 修复](../../../server-results/a5-setup/20261120_214build/results/27_qwen35_inductor_without_index_fix.log)。

### 7.5 误差量级判定

项目没有适用于所有输入的统一 logprob 硬阈值，需要结合分叉点候选间隔、固定输入和标准任务判断。本次两个长输出的分叉均为近似平票处的 argmax 翻转：

| Prompt | eager 分叉点 Top1/Top2 间隔 | 完整修复分叉点 Top1/Top2 间隔 |
|---|---:|---:|
| 人工智能发展历史 | 0.2500 | 0（保存精度下并列） |
| 天空为什么是蓝色 | 0.1250 | 0（保存精度下并列） |

分叉前共同候选的 logprob 平均绝对差为 0.0452～0.0719，最大差为 0.3750，Top-5 重合率为 98%～100%。这与已有 a5-28 Qwen3.5-0.8B 结果（平均 0.0500、最大 0.5000、Top-K 99.12%，MMLU 63.50%→64.00%）属于同一差异量级，没有显示出新的系统性精度下降。

因此，当前没有证据要求继续定位新的精度问题。但这只是 5 组 prompt 的专项验证，不等同于完成正式精度验收；正式验收仍需按测试矩阵执行 8 组固定输入两轮生成和标准任务精度评估。分叉后的 logprob 不用于直接比较，因为两条路径的上下文已经不同。
