# Qwen3.8-27B-W8A8：eager、default 与 Inductor 数值一致性定位

## 1. 当前结论

本次问题首先是**不同执行路径之间的数值一致性不足**，不能直接表述为 Inductor 的数学精度一定更差。

- eager 与原始 Inductor 的 8 组固定输入均未保持完整 token 一致，logprob 超出测试容差。
- eager 与 default 本身也存在明显差异，因此 default 不是与 eager 逐位相同的参考路径。
- default 与原始 Inductor 也不一致；差异来自 Inductor 为部分计算生成的 Triton kernel，而不是两者共享的 CANN 融合算子。
- 任务集使用相同样本，Inductor 的 MMLU、GSM8K 分数没有下降，但这不能替代固定输入和 logprob 检查。
- sigmoid 中间舍入原型曾使 default 与 Inductor 的一致数从 0/8 提升到 4/8，但由于修改会作用于所有经过 TE 代码生成入口的 BF16/FP16 sigmoid，作用范围过大，已完整撤回。
- 当前没有保留本次精度修复代码，也没有完成 eager 与编译路径之间的最终修复。

追踪表关联项：O-21。与 O-18 的 Qwen3-0.6B RMSNorm 差异、W-01 的 Norm+Quant 融合差异和 R-03 的 launcher 性能问题相关，但不是同一个问题。

环境：

- a5-25，Ascend950DT，TP2；

- torch 2.13.0+cpu；

- `temperature=0`、`seed=0`、关闭 prefix cache；

三条路径的含义：

| 路径 | 含义 |
|---|---|
| eager | `enforce_eager=True`，不执行编译优化 |

## 4. default 与 Inductor 的实际算子选择

下表列出本次生成图中与定位直接相关的实现，而不是把 Inductor 笼统视为“全部使用 Triton”。

| 计算位置 | default | 原始 Inductor | 差异 |
|---|---|---|---|
| sigmoid 与后续乘法 | 保留 `aten.sigmoid`、`aten.mul`，交给 AscendCompiler/CANN 路径 | 生成 FP32 sigmoid + 乘法的 Triton 融合 kernel，最后写回 BF16 | 原始 Inductor 没有保留 sigmoid 的 BF16 中间舍入 |
| 独立的 `npu_rms_norm` | 调用 CANN 原生 `npu_rms_norm` | 展开为 FP32 平方、平均、`rsqrt` 和乘法，再生成 Triton kernel | 归约、倒数平方根和舍入实现不同 |
| 满足条件的 AddRMSNorm + DynamicQuant | CANN `npu_add_rms_norm_dynamic_quant` | 同一个 CANN `npu_add_rms_norm_dynamic_quant` | default 与 Inductor 在此没有实现差异 |
| 其他 `npu_dynamic_quant` | CANN 原生实现 | 保留 CANN 原生调用 | 没有 Triton 重写 |
| `npu_quant_matmul` | CANN 原生实现 | 保留 CANN 原生调用 | 没有 Triton 重写 |
| `npu_swiglu` | CANN 原生实现 | 保留 CANN 原生调用 | 没有 Triton 重写 |
| `all_reduce` | vLLM 通信算子 | 保留 vLLM 通信算子调用 | 没有 Triton 重写 |

原始 Inductor 中 sigmoid + 乘法的实际生成代码为：

```python
tmp0 = tl.load(in_ptr0 + x0).to(tl.float32)
tmp1 = tl.load(in_ptr1 + x0).to(tl.float32)
tmp2 = tl.sigmoid(tmp1)
tmp3 = tmp0 * tmp2
tl.store(out_ptr0 + x0, tmp3)
```

独立 RMSNorm 的展开公式为：

```python
x = x.float()
rstd = torch.rsqrt(x.pow(2).mean(-1, keepdim=True) + epsilon)
output = (x * rstd * weight).to(dtype)
```

共享的 CANN NormQuant 融合调用为：

```python
buf9 = torch.ops.npu.npu_add_rms_norm_dynamic_quant.default(...)
```

需要特别区分：**独立 RMSNorm 与 CANN NormQuant 融合算子内部的 RMSNorm 不是同一个归因对象。**只有满足特定 AddRMSNorm + DynamicQuant 组合的位置才会进入该融合算子。

## 5. 受控实验

为缩短诊断时间，后续固定输入实验使用相同的 8 组输入、最多 128 tokens。原始实验最晚的首个分叉位置为 74，因此 128 tokens 能覆盖全部原始分叉点。

### 5.1 三条原始路径的两两比较

| 比较 | token 一致 | logprob 平均绝对差 | logprob 最大绝对差 |
|---|---:|---:|---:|
| eager vs 原始 Inductor | 0/8 | 0.338180 | 2.888581 |
| eager vs default | 0/8 | 0.332291 | 7.374593 |
| default vs 原始 Inductor | 0/8 | 0.384162 | 7.437063 |

这组结果说明：

- default 与 eager 本身不相同；
- 原始 Inductor 与 default 也不相同；
- 不能只检查 Inductor 与 default 中的一组，就把剩余差异全部归给同一个算子。

### 5.2 图捕获、RMSNorm 和 NormQuant 对照

| 实验 | 比较 | 结果 |
|---|---|---|
| Inductor 改用 `cudagraph_mode=NONE` | 与原始 Inductor 比较 | token、文本、logprob 完全相同 |
| Inductor 保留原生 RMSNorm，其余不变 | eager vs Inductor | 仍为 0/8；平均差 0.366594，最大差 2.888581 |
| Inductor 不执行 CANN NormQuant 图替换，其余不变 | eager vs Inductor | 仍为 0/8；平均差 0.409122，最大差 7.874987 |

结论：

- ACLGraph 捕获和回放不是本次差异来源。
- 单独保留原生 RMSNorm 不能解决问题。
- 单独取消 CANN NormQuant 融合也不能解决问题；该实验只是诊断，不是修复方案。

### 5.3 sigmoid 与 RMSNorm 的组合对照

以 default 为参考：

| Inductor 改动 | token 一致 | logprob 平均绝对差 | logprob 最大绝对差 |
|---|---:|---:|---:|
| 原始版本 | 0/8 | 0.384162 | 7.437063 |
| 只保留原生 RMSNorm | 0/8 | 0.418357 | 7.437063 |
| 只在 Triton sigmoid 后补 BF16 中间舍入 | 4/8 | 0.159174 | 2.499998 |
| sigmoid 补中间舍入，同时保留原生 RMSNorm | 8/8 | 0.0 | 0.0 |

这组结果说明：

- sigmoid 中间舍入原型的独立改善最明显；
- 单独调整 RMSNorm 没有改善，但它影响 sigmoid 修复后剩余的差异；
- 两项同时处理后，default 与 Inductor 的 8 组输出完全一致。

最后一项中的原生 RMSNorm 只是诊断手段，不是要求保留的最终修复方式。

## 6. CANN NormQuant 融合与 eager 的差异

eager 使用：

```text
npu_add_rms_norm
→ 保存 BF16 Norm 中间结果
→ npu_dynamic_quant
```

编译路径可以把满足条件的部分替换为：

```text
npu_add_rms_norm_dynamic_quant
```

相同输入的算子级比较显示：

- residual 逐元素完全一致；
- scale 不完全一致；
- INT8 输出存在差异，通常为 1～2 个整数值。

例如，随机输入 `(128, 5120)` 的三组种子中，融合与非融合的 INT8 输出分别有约 3.2 万、3.0 万、3.2 万个元素不同；残差输出均完全一致。

已有 W-01 的高精度参考实验还表明，融合实现的 scale 在某些指标上更接近 FP64 参考。因此这里首先是一个**实现切换带来的数值一致性差异**，不能仅凭 eager 与融合结果不同就断言融合算子数学精度更差。

该融合用于解释 eager 与编译路径之间的差异，不是 default 与 Inductor 之间的差异来源，因为 default 和 Inductor 共用同一个 CANN 融合算子。目前尚未证明它是 eager 与 default 之间唯一的差异来源。

## 7. 两个差异的详细说明

本节展开 sigmoid 和 RMSNorm 两项差异。它们都发生在 default 与 Inductor 的共享 CANN 调用之外，但表现和证据强度不同。

### 7.1 sigmoid 与后续乘法的中间舍入

#### 7.1.1 两条路径分别选择了什么实现

default 的输入计算图保留两个独立节点：

```text
aten.sigmoid
→ aten.mul
```

它们被交给 AscendCompiler/CANN 路径，不经过 TE 的 sigmoid Triton 代码生成。

Inductor 则把这两个节点融合到一个 Triton kernel。原始生成代码为：

```python
tmp0 = tl.load(in_ptr0 + x0).to(tl.float32)  # 读取 value，并转成 FP32
tmp1 = tl.load(in_ptr1 + x0).to(tl.float32)  # 读取 gate 输入，并转成 FP32
tmp2 = tl.sigmoid(tmp1)                      # FP32 计算 sigmoid
tmp3 = tmp0 * tmp2                           # FP32 直接相乘
tl.store(out_ptr0 + x0, tmp3)                # 最后写回 BF16
```

因此，Inductor 的融合确实减少了中间结果的读写，但也改变了舍入发生的时机。

#### 7.1.2 具体少了哪一次舍入

把参考路径简化成下面的计算过程：

```text
gate_fp32 = sigmoid(x)
gate_bf16 = bf16(gate_fp32)
output = bf16(value × gate_bf16)
```

原始 Inductor 融合后相当于：

```text
gate_fp32 = sigmoid(x)
output = bf16(value × gate_fp32)
```

区别就是 `bf16(gate_fp32)` 这一次中间转换。即使最后输出都保存为 BF16，两种计算也不等价，因为第二次乘法使用的 gate 精度不同。

这里不能仅凭这一点判断哪种实现数学上更准确。FP32 连续计算可能更接近高精度结果；本次确认的是它与参考路径不一致。

#### 7.1.3 原型具体修改了什么

原型没有关闭融合，也没有把 sigmoid 回退给 CANN，而是在 TE 的 sigmoid 代码生成函数中补充低精度往返转换：

```python
@maybe_upcast_float32(convert_output=False)
def sigmoid(x):
    schedule_node = getattr(V.kernel, "current_node", None)
    dtype = getattr(getattr(schedule_node, "node", None), "dtype", None)
    result = f"tl.sigmoid({x})"
    if dtype in (torch.bfloat16, torch.float16):
        result = f"{result}.to({_upstream_triton_type(dtype)}).to(tl.float32)"
    return result
```

BF16 情况下，生成的逻辑相当于：

```python
gate = tl.sigmoid(x)
gate = gate.to(tl.bfloat16).to(tl.float32)
output = value * gate
```

转回 FP32 是为了继续后续融合计算，但刚刚那次 BF16 舍入已经保留。整个过程仍在同一个 Triton kernel 内完成。

#### 7.1.4 微基准和模型证据

微基准直接比较三种实现：

1. 参考路径的 sigmoid + 乘法；
2. 原始 FP32 连续融合；
3. 在 sigmoid 后补 BF16 往返舍入的融合。

输入覆盖 `(8,3072)`、`(128,3072)`、`(8192,3072)` 三种形状和 3 个随机种子。结果是：

- 原始融合在每种输入上都有大量元素与参考不同；
- 补舍入后的融合在全部 9 组输入上与参考逐元素完全相同。

模型级结果则是 default 与 Inductor 的一致数从 0/8 提升到 4/8，logprob 平均绝对差从 0.384162 降至 0.159174，最大差从 7.437063 降至 2.499998。这证明该差异会影响真实模型，但不是唯一来源。

#### 7.1.5 为什么仍然撤回

原型读取的是当前调度节点的 dtype，并没有判断 sigmoid 是否位于本次目标融合结构中。因此它会作用于所有经过该 TE 入口的 BF16/FP16 sigmoid，包括独立 sigmoid 和其他模型。

对独立 sigmoid，这种转换可能只是冗余指令；对其他融合结构，也需要重新验证数值和性能。由于没有完成这些回归，且全局规则的作用范围过大，该原型已完整撤回。文档保留其代码和结果，只作为定位证据，不代表当前源码包含此修改。

### 7.2 独立 RMSNorm 的原生与 Triton 实现差异

#### 7.2.1 这里讨论的是哪一个 RMSNorm

模型中并不是所有 RMSNorm 都进入 `npu_add_rms_norm_dynamic_quant`。只有满足特定 AddRMSNorm + DynamicQuant 组合的位置才进入 CANN 融合算子。

本节讨论的是没有进入该组合的独立 `npu_rms_norm`，例如计算图中原生形式为：

```python
npu_rms_norm = torch.ops.npu.npu_rms_norm(input, weight, epsilon)
```

default 保留这个调用，直接执行 CANN 原生实现。Inductor 则把它展开成更基础的计算，再生成 Triton kernel。

#### 7.2.2 Inductor 展开后的具体计算

当前展开实现为：

```python
dtype = x.dtype
x = x.float()
rstd = torch.rsqrt(x.pow(2).mean(-1, keepdim=True) + epsilon)
output = (x * rstd * weight).to(dtype)
return output, rstd
```

它包含以下计算：

1. 把输入转换为 FP32；
2. 对最后一维求平方；
3. 求平方平均值；
4. 加 `epsilon` 后计算倒数平方根；
5. 乘输入和权重；
6. 转回原始 BF16 输出。

CANN 原生实现完成的是同一个数学公式，但不要求其内部归约顺序、倒数平方根指令和中间舍入与 Inductor 完全相同。

#### 7.2.3 差异可能来自哪些具体步骤

目前需要区分三个步骤：

- **归约**：平方值按什么顺序累加，会影响 FP32 末位；
- **rsqrt**：原生实现和 `tl.rsqrt` 可能相差一个 FP32 ULP；
- **输出舍入**：归一化结果在什么时刻转换成 BF16，会影响后续计算和量化输入。

因此，这不是“Inductor 忘记写 RMSNorm 公式”，而是相同公式在不同实现下产生了数值末位差异。现有结果也没有证明 Inductor 的数学精度一定更差。

#### 7.2.4 为什么单独调整 RMSNorm 没有改善

以 default 为参考：

- 原始 Inductor 的平均 logprob 绝对差为 0.384162；
- 只把独立 RMSNorm 保留为原生实现后，平均差为 0.418357；
- 最大差仍为 7.437063，token 一致数仍为 0/8。

以 eager 为参考，单独保留原生 RMSNorm 也仍为 0/8，平均差为 0.366594。

所以不能把 RMSNorm 单独描述为唯一原因，也不能把原生回退当作修复。

#### 7.2.5 为什么组合实验又完全一致

在 sigmoid 修复基础上再保留原生 RMSNorm 后，default 与 Inductor 达到：

- token 8/8 一致；
- 文本 8/8 一致；
- 所有保留下来的公共 logprob 平均、最大绝对差均为 0。

这说明 RMSNorm 影响的是 sigmoid 修复后剩余的差异。两项差异存在组合关系：只处理 RMSNorm 时，sigmoid 的差异仍然存在，整体指标不会因此自动改善。

组合实验同时证明了归因边界：default 与 Inductor 的剩余差异确实与独立 RMSNorm 的实现选择有关。但它没有证明生产修复必须回退原生算子，也没有解决 eager 与编译路径之间的差异。

#### 7.2.6 尚未完成的修复工作

如果要保留 Inductor/Triton 实现并严格匹配 default，需要继续：

1. 单独比较原生与 Triton 的 `rstd`，确定倒数平方根差异；
2. 固定 `rstd` 后检查平方和归约顺序；
3. 检查 Norm 输出的 BF16 舍入时机；
4. 修改 Triton kernel 或数值 helper，而不是回退原生 RMSNorm；
5. 用不依赖原生回退的组合实验重新验证 default 与 Inductor 的 8/8 一致性。

当前这些工作尚未完成，因此 RMSNorm 只记录为已确认的数值实现差异，不记录为已修复问题。

## 8. 实验中如何规避这两个差异

本节只记录诊断实验的操作方法。它们用于证明差异来源，不是最终产品修复。

### 8.1 sigmoid：修改 TE 代码生成并使用独立缓存

实验直接修改了：

```text
pytorch/torch_npu/_inductor/triton_experimental/codegen/triton.py
```

在 `NPUTritonKernelOverrides.sigmoid()` 中，对调度输出为 BF16/FP16 的 sigmoid 增加“低精度转换后再转回 FP32”的逻辑。具体代码见 7.1.3。

由于 Python 运行时使用已安装的 `torch_npu` 副本，实验同时同步了：

```text
conda_inductor_2.14/lib/python3.12/site-packages/torch_npu/_inductor/triton_experimental/codegen/triton.py
```

也就是说，不能只改源码树而不处理已安装副本，否则实际运行可能仍使用旧代码。同步后使用文件比较确认两处内容一致。

该实验使用新的编译缓存目录，避免读到修改前生成的 Triton kernel。验证分为两层：

1. 直接编译 sigmoid + 乘法微基准，检查实际输出和生成代码；
2. 启动完整 Qwen3.8-27B-W8A8，运行相同 8 组固定输入并与 default 比较。

原型通过后，已撤回上述源码和已安装副本中的修改，并恢复原始文件。后续复现实验时，不应假设当前工作区仍包含这项修改。

### 8.2 RMSNorm：在所有相关进程中取消 `npu_rms_norm` 分解

RMSNorm 实验没有修改产品源码，而是增加了一个诊断用 `sitecustomize.py`：

```python
import os

import torch
import torch_npu
from torch_npu._inductor import decomposition


def keep_native_rms_norm():
    from torch._inductor.decomposition import decompositions

    decompositions.pop(torch.ops.npu.npu_rms_norm.default, None)
    decompositions.pop(torch.ops.npu.npu_rms_norm_backward.default, None)
    print(f"NATIVE_RMSNORM_DECOMP_DISABLED pid={os.getpid()}", flush=True)


decomposition._override_rms_norm_decomp = keep_native_rms_norm
keep_native_rms_norm()
```

它的作用是：

- 替换 TE 注册 RMSNorm 分解的函数；
- 注册分解表时不再把 `npu_rms_norm` 展开成平方、平均和 `rsqrt`；
- 让该独立 RMSNorm 保留为 CANN 原生调用。

之所以使用 `sitecustomize.py`，是因为 TP2 使用 spawn 创建 worker。只修改父进程中的分解表不足以保证两个 worker 都应用诊断规则；Python 启动时自动导入 `sitecustomize`，可以使父进程、EngineCore 和两个 TP worker 都执行同一修改。

实际运行时通过 `PYTHONPATH` 指向该诊断文件所在目录：

```text
server-scripts/benchmark-diagnosis/qwen38_accuracy_native_rmsnorm/sitecustomize.py
```

### 8.3 `env.sh` 对 `PYTHONPATH` 的影响

这里有一个必须保留的实验细节：`env.sh` 会执行 `unset PYTHONPATH`。

第一次在 `source env.sh` 之前设置 `PYTHONPATH`，导致实际运行没有导入诊断模块。生成代码中仍然存在 `tl.rsqrt`，证明该次“原生 RMSNorm”对照没有生效。

修正后，运行包装器在加载 `env.sh` 之后，再通过命令设置 `PYTHONPATH`：

```bash
source env.sh
# runtime.py exec 内部再次加载 env.sh，因此把 env 放在最终执行命令上
runtime.py exec ... -- \
  env PYTHONPATH=<诊断目录> python correctness.py generate ...
```

这样才能确保 spawn 子进程也继承诊断路径。

本次有效对照使用两个证据确认规则真正生效：

- 父进程和两个 TP worker 均打印 `NATIVE_RMSNORM_DECOMP_DISABLED`；
- 生成代码中的 `tl.rsqrt` 从普通 Inductor 的 2 处降为 0，同时出现 2 处原生 `npu_rms_norm` 调用。

实验同样使用独立缓存，避免复用取消分解前生成的代码。

### 8.4 组合实验如何同时规避两项差异

组合实验同时满足：

1. 已安装副本中的 TE sigmoid 代码生成包含中间舍入原型；
2. 最终运行命令通过 `PYTHONPATH` 加载 RMSNorm 诊断模块；
3. 父进程、EngineCore 和两个 TP worker 使用同一规则；
4. 使用新的编译缓存；
5. 其他模型、TP2、输入、随机种子和 Inductor 配置保持不变。

因此，组合实验与 default 的 8/8 一致不是来自改变输入或关闭图捕获，而是同时消除了 sigmoid 和独立 RMSNorm 两处实现差异。

这两项操作都只用于诊断。sigmoid 原型因作用范围过大已撤回；RMSNorm 的 `sitecustomize` 方法保留在临时诊断脚本中，不属于生产代码，也不应作为正式修复方式。

## 9. 问题性质与后续建议

当前结果支持“数值一致性差异”，但不足以把所有差异都称为真正的精度 bug。判断是否需要修复应先明确目标：

- 若要求与参考路径逐位一致，则需要处理中间舍入、归约和量化实现差异；
- 若只要求数学精度和任务表现可接受，则还需要高精度参考及更多任务集证据，不能仅凭 token 或 logprob 不同判定实现错误。

后续建议：

1. 不直接恢复已撤回的全局 sigmoid 原型；先缩小适用条件并评估独立 sigmoid 的性能影响。
2. RMSNorm 分别测量归约、`rsqrt` 和输出舍入，不以原生回退作为最终修复。
3. 若必须让 eager 与 CANN NormQuant 融合逐位一致，需要修改 CANN 融合 kernel，或完成一个通过逐元素验证的替代融合 kernel；当前工作区没有该 CANN kernel 的源码。
4. 补充 default 与 eager 的任务集对照，避免只用 logprob 判断实际答题精度。
5. 任何修复都应重新运行完整 1024-token 固定输入和相同任务集，不能把本次 128-token 诊断结果直接写成正式验收通过。
