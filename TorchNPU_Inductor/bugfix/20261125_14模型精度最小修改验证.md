# 14 个模型 Inductor 精度最小修改验证

## 1. 结论

在 a5-25 容器 `inductor_214build_z00896543_20261120_1546` 中，基于《[20261122_Qwen3.8-27B-W8A8精度定位](20261122_Qwen3.8-27B-W8A8精度定位.md)》的候选修改完成了逐项、组合和删减验证。

主要结论：

1. 上一轮 14 个有效对比模型均已完成**完整 1024-token、Top-20、两轮生成**验证。使用 sigmoid 中间舍入、保留原生 RMSNorm、关闭 NormQuant 的三组合诊断后，14 个模型全部达到：
   - token **8/8**；
   - `logprob_within_tolerance=true`；
   - 平均及最大 logprob 绝对差均为 **0.0**；
   - 8 个 prompt 的 `pr_failure` 全部为 `null`；
   - 两轮生成均满足 `token_stable=true`。
2. 不是所有模型都需要三项修改。按实际生成代码和删减实验，最小有效诊断组合分为：
   - **仅原生 RMSNorm**：6 个模型；
   - **原生 RMSNorm + sigmoid 中间舍入**：6 个模型；
   - **原生 RMSNorm + sigmoid 中间舍入 + 关闭 NormQuant**：2 个模型。
3. **尚未找到可保留的通用产品补丁。**原生 RMSNorm 的 `sitecustomize` 注入仍是诊断回退，不能作为最终产品修复；RMSNorm 单行输出舍入、限定 `npu_swiglu` 的写法及 `1/sqrt`、`pow(x,-0.5)` 替代均未通过验证。

这里的“最小”限于本次候选集合和实际测试证据，不表示已经证明其他实现不存在更小修改。

## 3. 三个修改点分别改了什么、为什么需要

这三个修改针对的是三个不同的数值实现差异，不能互相替代。它们的目标是让参考路径与 Inductor 的计算顺序和中间舍入保持一致，而不是预先断言哪一种实现的数学精度一定更高。

### 3.1 sigmoid 中间舍入：恢复融合前丢失的一次 BF16/FP16 舍入

在 default 路径中，sigmoid 和后续乘法是分开的节点：

```text
aten.sigmoid → aten.mul
```

以 BF16 为例，参考路径可以简化为：

```text
gate_fp32 = sigmoid(x)
gate_bf16 = bf16(gate_fp32)
output = bf16(value × gate_bf16)
```

Inductor 则把 sigmoid 和乘法融合到一个 Triton kernel，原始生成逻辑为：

```python
tmp0 = tl.load(in_ptr0 + x0).to(tl.float32)
tmp1 = tl.load(in_ptr1 + x0).to(tl.float32)
tmp2 = tl.sigmoid(tmp1)
tmp3 = tmp0 * tmp2
tl.store(out_ptr0 + x0, tmp3)
```

这里直接在 FP32 中完成 sigmoid 和乘法，最后才写回 BF16，少了参考路径中 sigmoid 输出先转成 BF16 的那一次中间舍入。即使最终输出类型相同，两种计算也不等价。

诊断修改是在 sigmoid 后补一次低精度往返转换：

```python
gate = tl.sigmoid(x)
gate = gate.to(tl.bfloat16).to(tl.float32)
output = value * gate
```

转回 FP32 是为了继续进行后续融合计算，但 BF16 舍入已经发生。这样可以保留 Triton 融合，同时使中间舍入时机与参考路径一致。

**为什么需要它：**27B-W8A8 的实验表明，只保留原生 RMSNorm 不能消除全部差异；sigmoid 舍入则明显改善了 default 与 Inductor 的一致性。它是组合实验中处理 sigmoid+乘法融合差异的必要部分，而不是用于提高 sigmoid 本身的数学精度。

**限制：**当前诊断原型位于 TE 代码生成入口，可能作用于经过该入口的 BF16/FP16 sigmoid。实际生成代码显示只有部分 sigmoid 增加了往返转换，但这仍不足以证明全局规则安全，因此产品化前必须进一步限定目标融合结构，不能直接把原型当成正式修复。

### 3.2 原生 RMSNorm：避免 Inductor 分解带来的 `rstd` 实现差异

这里讨论的是**独立的 `npu_rms_norm`**，不是 NormQuant 融合算子内部的 RMSNorm。

Inductor 当前会把独立 RMSNorm 分解为：

```python
dtype = x.dtype
x = x.float()
rstd = torch.rsqrt(x.pow(2).mean(-1, keepdim=True) + epsilon)
output = (x * rstd * weight).to(dtype)
```

默认路径则直接调用 CANN 原生 `npu_rms_norm`。两者数学公式相同，但平方和的归约顺序、倒数平方根指令和中间实现并不要求逐位相同。

诊断实验通过 `sitecustomize` 取消 `npu_rms_norm` 及其 backward 的 Inductor 分解，使独立 RMSNorm 保留为原生 CANN 调用。原定位文档中的核心操作是：

```python
decompositions.pop(torch.ops.npu.npu_rms_norm.default, None)
decompositions.pop(torch.ops.npu.npu_rms_norm_backward.default, None)
```

**为什么需要它：**当 sigmoid 舍入已经处理后，独立 RMSNorm 成为 default 与 Inductor 之间剩余差异的重要来源。两者组合后，default 与 Inductor 达到 8/8 且 logprob 差值为 0，证明这条实现路径确实影响最终输出。

本轮微基准进一步说明，原生与 Triton 的部分 `rstd` 会相差约 1 个 FP32 ULP。固定使用原生 `rstd` 后，连续 FP32 乘法可以与原生输出逐元素一致，因此问题不是简单的“公式写错”，也不能靠提前增加一次 BF16 输出舍入解决。

**限制：**保留原生 RMSNorm 是用于证明数值路径的诊断回退，不是最终产品修复。它改变了 Inductor 的分解和代码生成方式，可能影响性能及其他图优化。后续若要保留 Triton 实现，需要继续处理归约和 `rstd` 的具体差异，而不是简单删除分解。

### 3.3 关闭 NormQuant 融合：使 eager 与编译路径重新经过相同的量化步骤

eager 中的相关计算是：

```text
npu_add_rms_norm
→ 保存 BF16 Norm 中间结果
→ npu_dynamic_quant
```

编译路径可以把满足条件的部分替换为：

```text
npu_add_rms_norm_dynamic_quant
```

这个融合改变了 Norm 中间结果的保存方式和量化实现。已有算子级比较显示，融合与非融合的 residual 可以完全一致，但 scale 不完全一致，INT8 输出也会相差少量整数值。因此，eager 与编译路径之间会出现数值差异。

诊断修改不是改用其他量化方式，而是只关闭这一图替换：

```python
additional_config = {
    "ascend_compilation_config": {
        "fuse_norm_quant": False,
    }
}
```

这样满足条件的图不再被替换成融合调用，回到与 eager 对应的分算子路径。实验没有使用 `custom_ops=none`，因为那会同时改变 RMSNorm 和其他 custom op 的选择，无法单独判断 NormQuant 的影响。

**为什么需要它：**default 与 Inductor 可以共享同一个 CANN NormQuant 融合算子，所以“default 与 Inductor 已经 8/8”并不能证明 eager 与 Inductor 也一致。27B-W8A8 的结果正好说明了这一点：sigmoid + 原生 RMSNorm 使 default 与 Inductor 完全一致，但 eager 与 Inductor 仍然失败；只有再关闭 NormQuant，eager 才达到 8/8。

**适用范围：**只有实际图中存在 `npu_add_rms_norm_dynamic_quant` 替换时，这个开关才有意义。27B-W8A8 和 35B-W8A8 的基线图中存在该调用，因此需要关闭；其他模型的生成代码中没有这个融合调用，关闭开关不会产生数值变化，应从各自最小组合中剔除。

### 3.4 为什么三个修改要按模型组合，而不是统一全开

| 修改点 | 主要处理的差异 | 与其他修改的关系 |
|---|---|---|
| sigmoid 中间舍入 | Triton 融合省略了参考路径中的 BF16/FP16 中间舍入 | 只影响实际包含目标 sigmoid+乘法融合的模型 |
| 原生 RMSNorm | Inductor 分解后的归约和 `rstd` 与 CANN 原生实现不同 | 处理独立 RMSNorm，不处理 NormQuant 内部实现 |
| 关闭 NormQuant | eager 的分算子量化路径与编译后的融合量化路径不同 | 只在实际发生 NormQuant 图替换时有效 |

因此，三项全开是便于统一验证的诊断组合，但不一定是每个模型的最小组合。最终需要通过实际生成代码判断开关是否生效，再通过删减实验确认它是否必需：

- sigmoid 和 NormQuant 都没有图影响的模型，只保留原生 RMSNorm；
- NormQuant 没有图影响的模型，保留原生 RMSNorm 和 sigmoid 舍入；
- 三个差异同时存在的 27B-W8A8、35B-W8A8，则必须保留三项。

这也解释了为什么本轮同时强调“14 个模型全部通过”和“没有通用产品补丁”：诊断组合已经证明这些数值差异可以被消除，但产品实现仍需分别处理 sigmoid 的作用范围和 RMSNorm 的 `rstd` 差异，不能简单把三个诊断开关固化到所有模型。

## 6. 产品化最小修改尝试

### 6.1 限定 sigmoid + RMSNorm 单行舍入

尝试将 sigmoid 舍入限制到 `npu_swiglu`，并用下面的 RMSNorm 输出舍入替代原生回退：

```python
output = ((x * rstd).to(dtype) * weight).to(dtype)
```

同时关闭 NormQuant。结果：

- eager token **0/8**，8 个 prompt 都是 decode logprob 超差；
- 引擎初始化耗时 1344 秒；
- 生成代码显示该 `npu_swiglu` 写法引入了新的 Triton SwiGLU kernel，并非只增加舍入，改变了原有执行路径；
- 该候选不作为修复保留。

结果目录：`qwen38_w8a8_128/scoped_rms_no_norm_quant_gpu90/`。

### 6.2 保留原 sigmoid 方式，仅替换 RMSNorm 单行舍入

为了隔离 RMSNorm 公式的影响，保留已验证有效的 sigmoid 方式，只加入上述 RMSNorm 单行舍入并关闭 NormQuant：

- eager token **5/8**，但 `logprob_within_tolerance=false`；
- 与“sigmoid + 关闭 NormQuant”的 5/8 相比没有解决剩余问题；
- 该公式不能替代原生 RMSNorm。

结果目录：`qwen38_w8a8_128/global_sig_rms_no_norm_quant_gpu90/`。

### 6.3 RMSNorm 微基准

对 `(8,3072)`、`(128,3072)` 和多个 seed 比较原生与 Triton：

- 原生与 Triton 的部分 `rstd` 相差约 1 个 FP32 ULP；
- 固定使用原生 `rstd` 后，连续 FP32 乘法与原生输出逐元素完全一致；
- 提前执行 `x*rstd` 的 BF16 舍入会产生大量额外差异，不能解释原生输出；
- `1.0 / torch.sqrt(...)` 与 `torch.rsqrt(...)` 的结果相同；
- `torch.pow(...,-0.5)` 在部分用例中减少差异，但仍未普遍匹配原生 `rstd` 和输出。

因此，RMSNorm 的剩余问题与 `rstd` 的实现细节有关，不能通过单行输出舍入解决。结果位于 `micro_rmsnorm/`。

## 7. 是否保留源码修改

本轮没有修改产品源码或服务器已安装的 `torch_npu` 副本。所有候选均通过临时诊断脚本和环境开关实施，未找到满足全部 14 个模型且作用范围可接受的通用产品补丁，因此**不保留产品代码修改**。

可以保留的最小实验结论是第 5 节的三类诊断组合。原生 RMSNorm 回退只用于证明数值路径，不将其包装成最终生产修复；全局 sigmoid 代码生成原型也需要进一步缩小适用条件后才能产品化。
