# Qwen3.8-27B-W8A8：RMSNorm 特化参数打包错误导致性能回退

## 1. 当前状态与结论边界

- **状态**：Triton-Ascend C launcher 修复已通过 A5 算子、模型 profiling 和官方非 profiling 性能验证，尚未合入正式分支。
- **根因**：`make_launcher(constants, signature, metadata)` 接收却未使用 `constants`。已从 TTIR 删除的特化参数仍被 C launcher 打包进设备参数缓冲区，导致后续隐藏 grid 参数偏移与二进制约定不一致。
- **本例性能机制**：设备把 grid 总量从 2048 错读为 10,485,760，使相同 RMSNorm tile 被重复处理约 5120 倍。由于取模寻址仍落在合法范围，且输出是相同结果的覆盖写，原始固定配置主要表现为性能回退而非数值错误，完整推导见 6.4。
- **修复方式**：Python 侧保留完整参数个数检查和解析；设备打包时将 `constants` 中的参数视为 `constexpr` 并跳过。常量特化、原融合内核、tile、grid 和自动调优全部保留。
- **验证结果**：保留 `r0_numel=5120` 常量时，原算子由约 378 ms 恢复至 **0.0895 ms**；模型 profiling 负载平均 TTFT 为 **14.504 s**，default 为 14.513 s。
- **归因边界**：根因已定位到启动参数打包，不再归因于非 2 次幂常量算术或 BiShengIR RMSNorm 指令生成。通用回归和正式合入仍需完成。

此前“非 2 次幂不写入 constants”的 Inductor 修改只是临时规避，已完整撤销。本文保留其定位价值，但不再将其作为最终修复。

本问题与 O-18 的 Qwen3-0.6B RMSNorm 数值末位差、W-01 的 Norm+Quant 融合数值差异均不同，后两者不覆盖本文。

## 3. 真实生成内核及其计算过程

Inductor 将相关计算节点融合后，生成一个 Triton Python 文件，再由 Triton-Ascend、`triton-opt` 和 `bishengir-compile` 生成 NPU 可执行程序。launcher 启动多个 program，并行处理输入的不同行。

### 3.1 从 Python 到 NPU 的编译链

IR（Intermediate Representation，中间表示）是源码转换为机器码过程中使用的结构化表达。MLIR 是承载这些表达的编译器框架，不同前缀代表不同操作集合：`tt` 表示 Triton 操作，`arith/math` 表示算术，`memref` 描述内存，`linalg` 描述结构化张量计算，`scf` 描述条件与循环。

本次涉及的主要层次为：

| 层次/文件 | 含义 | 本次排查用途 |
|---|---|---|
| Triton `.py` | 自动生成的 Python kernel | 检查 RMSNorm 数学计算和寻址 |
| TTIR `.ttir` | 接近 Triton 语义的 IR，包含指针、张量、`tt.load`、`tt.reduce` | 判断慢快版本的数学操作是否不同 |
| TTAdapter `.ttadapter` | 转换为 `memref`、`memref.copy`、`linalg.reduce` 等形式 | 检查内存访问、归约和控制流 |
| BCMLIR `.bcmlir` | 后续 BiSheng 编译阶段前的文本 MLIR | 确认送入后端前的计算结构 |
| `.npubin` | NPU ELF 机器码 | 比较静态指令和实际设备二进制 |
| C launcher | CPU 侧参数解析、设备参数打包和 kernel 启动 | 检查主机与设备对参数布局的约定 |

其中 `.bcmlir` 是文本 MLIR，`.mlirbc` 是二进制编码的 MLIR，两者不是同一文件。设备 kernel 负责数学计算，C launcher 负责准备输入输出地址、标量、grid 等参数并启动设备；本次最终问题位于后者。

### 3.2 原始真实生成内核

原始真实生成文件见 [generated_kernel.py](../../../../server-results/benchmark/20261117_A5机器模测_Inductor矩阵/results/20261119_qwen38_27b_w8a8_profile_32768_1024_event_windows_01/comparison/generated_kernel.py)。

以下是该文件第 23～79 行的完整计算函数，未作改写：

```python
@triton.jit
def triton_unk_fused_add_npu_dynamic_quant_npu_rms_norm_0(in_ptr0, in_ptr1, out_ptr1, out_ptr2, xnumel, x0numel, r0_numel, XBLOCK : tl.constexpr, R0_BLOCK : tl.constexpr):
    total_thread = 64
    group_id = tl.program_id(0)
    r0_numel = 5120
    x_g_tile0 : tl.constexpr = (16384) if (16384) < (XBLOCK) else (XBLOCK)
    real_block_x0 : tl.constexpr = x_g_tile0
    x0_blocks = (x0numel + real_block_x0 - 1) // real_block_x0
    group_size = 1
    group_base = group_id
    for i in range(group_size):
        rbase = tl.arange(0, R0_BLOCK)[None, :]
        x0offset = (group_base + i) % x0_blocks * real_block_x0
        x0index = x0offset + tl.arange(0, real_block_x0)[:, None]
        x0 = x0index
        x0mask = x0index < x0numel
        xmask = x0mask
        r0_base = tl.arange(0, R0_BLOCK)[None, :]
        rbase = r0_base
        rnumel = r0_numel
        RBLOCK: tl.constexpr = R0_BLOCK
        _tmp4 = tl.full([real_block_x0, R0_BLOCK], 0, tl.float32)
        for r0_offset in tl.range(0, r0_numel, R0_BLOCK):
            r0_index = r0_offset + r0_base
            r0_mask = r0_index < r0_numel
            roffset = r0_offset
            rindex = r0_index
            r0_1 = r0_index
            tmp0 = tl.load(in_ptr0 + (r0_1 + 5120*x0), r0_mask & x0mask, eviction_policy='evict_last', other=0.0).to(tl.float32)
            tmp1 = tmp0.to(tl.float32)
            tmp2 = tmp1 * tmp1
            tmp3 = tl.broadcast_to(tmp2, [real_block_x0, R0_BLOCK])
            tmp5 = _tmp4 + tmp3
            _tmp4 = tmp5
        tmp4 = tl.sum(_tmp4, 1)[:, None]
        for r0_offset in tl.range(0, r0_numel, R0_BLOCK):
            r0_index = r0_offset + r0_base
            r0_mask = r0_index < r0_numel
            roffset = r0_offset
            rindex = r0_index
            r0_1 = r0_index
            tmp6 = tl.load(in_ptr0 + (r0_1 + 5120*x0), r0_mask & x0mask, eviction_policy='evict_first', other=0.0).to(tl.float32)
            tmp14 = tl.load(in_ptr1 + (r0_1), r0_mask, eviction_policy='evict_last', other=0.0).to(tl.float32)
            tmp7 = tmp6.to(tl.float32)
            tmp8 = tl.full([1, 1], 5120.0, tl.float32)
            tmp9 = (tmp4 / tmp8)
            tmp10 = tl.full([1, 1], 1e-06, tl.float32)
            tmp11 = tmp9 + tmp10
            tmp12 = tl.rsqrt(tmp11)
            tmp13 = tmp7 * tmp12
            tmp15 = tl.full([1, 1], 1.0, tl.float32)
            tmp16 = tmp14 + tmp15
            tmp17 = tmp16.to(tl.float32)
            tmp18 = tmp13 * tmp17
            tmp19 = tmp18.to(tl.float32)
            tl.store(out_ptr1 + (r0_1 + 5120*x0), tmp19, r0_mask & x0mask)
            tl.store(out_ptr2 + (r0_1 + 5120*x0), tmp19, r0_mask & x0mask)
```

实际运行配置为：

```text
XBLOCK=4
R0_BLOCK=5120
num_warps=16
grid=2048
```

输入为 8192×5120 BF16。每个 program 处理 4 行，2048 个 program 共处理 8192 行。函数第一次读取输入并计算每行平方和，随后计算倒数均方根，第二次读取输入，完成归一化和权重乘法，最后写两个 BF16 输出。

## 4. Profiling 定位

为避免完整负载 trace 过大，分别采集 default 和 Inductor 的 8 条并发流式请求：prefill 在所有请求收到首 token 后停止，decode 在所有请求从 128 个 token 增长到 256 个 token 的窗口内采集。

rank0、相同 8192×5120 形状的直接比较：

| 路径与算子 | 次数 | 平均单次耗时 | 累计耗时 |
|---|---:|---:|---:|
| default：原生 `RmsNorm` | 32 | 48.03 μs | 1.537 ms |
| Inductor：`...fused_add_npu_dynamic_quant_npu_rms_norm_0` | 32 | 374222.77 μs | 11.975 s |

QuantBatchMatmulV3、FusedInferAttentionScore、ChunkGatedDeltaRuleFwdH 在两条路径基本持平；原生 `AddRmsNormDynamicQuantV2` 在 default 和 Inductor 中分别约 104.37 和 104.27 μs。异常集中在生成的 RMSNorm 融合内核，而不是量化矩阵乘、注意力或原生量化融合算子普遍退化。

## 5. 定位过程中的无效方向

### 5.1 误判 grid 重复计算

早期把 profiling 的 Block Num=64 当成逻辑 grid，并将静态代码中的候选值当作最终运行值，推测多个 block 重复处理相同 tile。launcher 动态 trace 后来确认 Python 侧实际 grid=2048，与 codegen 的 `npu_dispatch_recipe` 一致；Block Num=64 是硬件核数。因此早期推测的“Python grid 配错导致重复”不成立。后续更深层实验发现，设备端确实发生重复 tile，但原因是 C 参数打包错位使设备读取到错误的 grid 循环上界，详见 6.4。

### 5.2 修改 tile 和一行一个 program

独立参考内核采用一行一个 program 时可以达到约 0.157 ms，于是尝试改写 Inductor 生成体。第一次补丁未命中目标模板，结果不能用于判断；第二次确认命中后，模型启动和独立算子测试超时。固定配置后虽能结束，但耗时约 981.9 ms，且后 3072 行错误。删除 group 外层也没有改善。

该实验后来证明：参考实现同时没有携带 Inductor 的 `r0_numel` 常量标记，不能把参考实现的收益单独归因于一行一个 program。

### 5.3 怀疑自定义 launcher

同一类一行一个 program 内核在标准 Triton launcher 下为 0.174 ms，在自定义 launcher 下为 981.9 ms，表面上指向 launcher。但关闭 `fast_launch`、调整 `mix_mode` 和 `num_stages` 均不能解释问题，grid 和参数也正确。

关键对照是：保留自定义 launcher，仅去掉常量标记后，同一内核恢复至 0.203 ms。此前标准 launcher 对照同时去掉了常量标记，因此不是只改变 launcher 的单变量实验。

上游 `Ascend/pytorch@24c4858c` 修复 static/fast launcher 的参数与网格映射，但当前问题在普通自定义 launcher 和快捷入口中均可复现，该提交不是直接修复。

## 6. 根因证据

### 6.1 常量标记只是表层触发条件

原生成文件包含：

```python
'constants': {'r0_numel': 5120}
```

去掉该字段确实能使同一原始内核从约 378 ms 降至 0.09 ms，但这只能证明它触发问题，不能证明常量算术优化本身有错。

慢、快两组使用完全相同的 `XBLOCK=4、R0_BLOCK=5120、num_warps=16、grid=2048`，数值最大绝对误差均为 0.03125。逐层比较编译产物后确认：

- 规范化 TTIR 的加载、平方、归约、`rsqrt` 和存储完全相同；唯一实质差异是慢版签名删除了已特化的 `r0_numel`，快版保留该运行时参数。
- TTAdapter 和 BCMLIR 的计算结构也相同，只有运行时标量参数及随后的 program-id 参数编号不同。
- 静态反汇编均为 580 行，慢版没有多出数千倍静态指令；动态执行次数的差异来自 6.4 所述设备端 grid-stride 循环。

### 6.2 相同二进制仍有快慢差异

进一步构造“保留 `r0_numel` 常量特化，同时增加一个普通运行时 dummy 参数”的版本。它与“运行时 `r0_numel`、无 divisibility 属性”的版本具有：

- 完全相同的规范化 TTAdapter；
- 完全相同的 BCMLIR；
- 完全相同的 `.npubin` SHA256：`2ec1bc641f70cf5d77cfe3940e91f407312b11f24881e2117c792346e045e8a6`。

但前者耗时 686.37 ms，后者仅 0.0897 ms。相同设备二进制仍因启动签名不同而表现不同，直接排除了 RMSNorm 指令生成是根因。

### 6.3 C launcher 没有使用 constants

Triton-Ascend 的 `third_party/ascend/backend/driver.py` 中，`make_launcher(constants, signature, metadata)` 接收了 `constants`，原实现却完全没有使用它。

因此，前端已经从 TTIR 删除的特化参数，在 C launcher 中仍按原 `signature` 作为普通 `i32` 打包进设备参数缓冲区，后续隐藏 grid 参数的偏移与二进制约定不一致。这解释了为什么仅改变签名和打包方式就能在相同二进制上产生巨大性能差。

正确行为是：Python 侧仍接收并解析完整参数列表，以保持参数个数检查；构造设备 kernel 参数缓冲区时跳过 `constants` 中的参数。

### 6.4 为什么本例主要表现为性能问题，而不是数值错误

#### 6.4.1 旧 C launcher 的真实参数结构

旧生成的 C++ 设备参数结构体仍包含 `arg6`，也就是已特化的 `r0_numel`：

```cpp
struct __attribute__((packed)) {
    void* syncBlockLock __attribute__((aligned(8)));
    void* workspace_addr __attribute__((aligned(8)));
    void* arg0 __attribute__((aligned(8)));
    void* arg1 __attribute__((aligned(8)));
    void* arg2 __attribute__((aligned(8)));
    void* arg3 __attribute__((aligned(8)));
    int32_t arg4 __attribute__((aligned(4)));
    int32_t arg5 __attribute__((aligned(4)));
    int32_t arg6 __attribute__((aligned(4)));
    int32_t gridX __attribute__((aligned(4)));
    int32_t gridY __attribute__((aligned(4)));
    int32_t gridZ __attribute__((aligned(4)));
    void* DTData __attribute__((aligned(8)));
};
```

其中 `arg0～arg3` 是输入、权重和两个输出指针，`arg4/arg5` 是 `xnumel/x0numel`，`arg6=r0_numel=5120`。常量版二进制已从签名删除 `arg6`，因此它认为 gridX 紧跟在 `arg5` 后面。

偏移对照如下：

| 偏移 | 常量版二进制期望 | 旧 launcher 实际写入 | 设备最终读到 |
|---:|---|---|---:|
| 56 | gridX | `r0_numel` | **5120** |
| 60 | gridY | 真正的 gridX | **2048** |
| 64 | gridZ | 真正的 gridY | **1** |

设备因此看到 `gridX=5120、gridY=2048、gridZ=1`，而不是 launcher Python 侧实际的 `2048、1、1`。输入、权重和输出指针位于前面的相同偏移，没有错位。

#### 6.4.2 错误 grid 被用作设备端循环上界

慢版真实反汇编包含：

```text
19c: ADDI       X3, X0, #56
1a0: LDP.b32    X3, X1, [X3], #0
1a4: LD_IO.b32  X2, [X0], #64, #0
1a8: MOV        X27, BLOCKID
1ac: MUL.s64    X1, X1, X3
1b4: MUL.s64    X1, X1, X2
...
37c: ADDI       X0, X27, #64
384: LD_IO.b64  X0, [X30], #-1928
388: CMP.LT.s64 X27, X0
38c: JUMPCI     #916
```

其语义可概括为 grid-stride 循环：

```cpp
total = gridX * gridY * gridZ;
for (int block_id = BLOCKID; block_id < total; block_id += 64) {
    process(block_id);
}
```

正确情况下：

```text
total = 2048 × 1 × 1 = 2048
每个硬件核执行 2048 ÷ 64 = 32 次
```

错位后：

```text
total = 5120 × 2048 × 1 = 10,485,760
每个硬件核执行 10,485,760 ÷ 64 = 163,840 次
逻辑工作量放大 5120 倍
```

这解释了为什么静态反汇编行数相同，实际耗时却相差数千倍：慢的不是单条 RMSNorm 指令，而是同一段设备代码被动态执行了远多于所需的次数。原算子约 377.85 ms 与修复后约 0.08995 ms 的比值与该放大倍数同量级；重复访问相同数据还会受到缓存和内存合并影响，因此不要求实测比值严格等于 5120。

#### 6.4.3 取模寻址使多出来的工作反复处理相同 tile

真实生成代码使用：

```python
x0offset = (group_base + i) % x0_blocks * real_block_x0
```

本次 `x0_blocks=2048`、`real_block_x0=4`。program-id 超过 2048 后会回绕：

```text
program 0    → 第 0～3 行
program 1    → 第 4～7 行
...
program 2047 → 最后 4 行
program 2048 → 再次处理第 0～3 行
program 2049 → 再次处理第 4～7 行
```

所以错误扩大的 grid 没有访问非法行，而是反复处理相同的 2048 个 tile。

#### 6.4.4 RMSNorm 的重复覆盖是幂等操作

每次 tile 计算都重新初始化局部累加器：

```python
_tmp4 = tl.full([real_block_x0, R0_BLOCK], 0, tl.float32)
```

随后重新读取相同输入、计算相同结果，并执行：

```python
tl.store(out_ptr1 + ..., tmp19, ...)
tl.store(out_ptr2 + ..., tmp19, ...)
```

这里不是 `output += value`，而是 `output = value`。因此重复执行的效果是：

```text
第一次：output = A
第二次：output = A
...
最后一次：output = A
```

这类“重复执行后最终状态与执行一次相同”的操作称为幂等操作。本次前 2048 个逻辑 program 已经计算并写回全部 8192 行，后续工作只是用相同结果重复覆盖相同地址，所以固定原配置下观察到的是巨大性能回退，而逐元素检查仍为 8192 行全部通过、两个输出最大绝对误差均为 0.03125。

#### 6.4.5 不能据此认为参数错位只有性能风险

本例“数值仍正确”依赖多个条件：错位主要影响 grid、错误上界大于正确值、取模寻址仍落在合法范围、计算没有跨重复轮次保留状态，并且输出是相同结果的覆盖写入。

其他 kernel 或其他参数布局仍可能出现数值错误：

- grid 上界变成 0 或过小，可能导致输出未写或只写一部分；
- 指针或数据标量错位，可能读取错误地址或错误参数；
- `output += value`、原子累加、原地更新等操作不是上述覆盖写，多次执行会改变结果；
- 多个特化参数同时错位时，不能再套用本例的单一 grid 放大推导。

因此，本例的算子数值通过只说明该形状和配置下的实际表现，不能把 C launcher 参数错位归类为“安全的纯性能问题”。最终修复仍必须同时保留数值回归。

## 7. 最终修复

最终修改位于 **Triton-Ascend**，不是 Inductor codegen：

```python
signature = {
    index: "constexpr" if index in constants or (index,) in constants else arg_type
    for index, arg_type in signature.items()
}
```

将特化参数临时标记为 `constexpr` 后，现有 C++ 生成逻辑会：

- 保留 Python 侧参数个数检查和解析；
- 在设备参数结构体及 `_launch(...)` 调用中排除该参数；
- 保留原常量编译机会，不影响其他合法特化。

此前“非 2 次幂归约长度不写入 constants”的 Inductor 规避已完整撤销，torch_npu codegen 恢复原样。最终 patch 见 [triton_ascend_launcher_constants.patch](../../../../server-results/benchmark/20261117_A5机器模测_Inductor矩阵/results/20261119_qwen38_27b_w8a8_grid_fix_01/triton_ascend_launcher_constants.patch)。

## 8. 修复后验证

### 8.1 实际重新生成的内核

最终修复后的真实模型模板见 [driver_fix_generated_kernel.py](../../../../server-results/benchmark/20261117_A5机器模测_Inductor矩阵/results/20261119_qwen38_27b_w8a8_grid_fix_01/driver_fix_generated_kernel.py)，其中仍明确包含：

```python
'constants': {'r0_numel': 5120}
```

使用 8192×5120 BF16 输入和 PyTorch 浮点参考结果检查原始常量版内核：

| 验证 | 平均耗时 | 数值结果 |
|---|---:|---|
| 固定原配置，保留常量，C launcher 修复 | **0.08995 ms** | 两个输出最大误差 0.03125 |
| 正常自动调优，保留常量，C launcher 修复 | **0.08953 ms** | 两个输出最大误差 0.03125 |
| 运行时参数回归，C launcher 修复 | **0.08974 ms** | 两个输出最大误差 0.03125 |

三者均为 8192 行全部通过；自动调优仍选择 `XBLOCK=4、R0_BLOCK=5120、grid=2048`。这同时证明常量优化得以保留，未特化路径没有因 driver 修改回退。

## 9. 上游修复与发布版本状态

以下状态核对于 2026-11-20。

### 9.1 官方已有同型 issue 和专门修复 PR

上游 [issue #2407](https://github.com/triton-lang/triton-ascend/issues/2407) 与本问题根因相同：value-folded 参数仍被 launcher 打包，后续参数错位 4 字节，persistent kernel 的 grid 参数因此被错读。

该 issue 的 SAM 示例中，循环上界由 48 错变为 `196×48×1=9408`。与本例的 `2048 → 5120×2048×1` 属于同一机制。它还记录了 in-place softmax 和 BatchNorm 训练的数值损坏，说明这类问题并不总是只影响性能。该 issue 于 2026-11-06 被机器人以 stale/not planned 关闭，不是因为专门修复 PR 已合入。

[PR #2387：skip value-folded arguments when packing launcher args](https://github.com/triton-lang/triton-ascend/pull/2387) 是专门修复：

- 2026-09-24 创建，2026-10-10 最后更新；
- 当前仍为 open，`merged_at=null`，且 `mergeable_state=dirty`；
- 修改 `driver.py`，新增 7 行、删除 2 行；
- 将 `(6,)` 形式的 constants 键与整数 signature 索引 `6` 归一化，再在设备参数结构体声明和初始化两个位置跳过这些参数。

本地 driver 补丁与 #2387 的实现形式不同，但目标一致，且已通过本报告的算子和模型验证。后续形成正式提交时，应优先对齐 #2387 的最小修改，并保留本次 Qwen3.8 回归证据。

### 9.2 最新 main 已通过 shared launcher 包含等价处理

不能仅凭 #2387 未合入就断言最新 main 仍存在该问题。上游 [PR #2685](https://github.com/triton-lang/triton-ascend/pull/2685) 于 2026-10-21 合入，使用 shared native runtime 替代旧的逐 kernel C++ launcher；对应当前代码提交为 [`0ab6bf7d621c`](https://github.com/triton-lang/triton-ascend/commit/0ab6bf7d621c8dbffd81c449a0ba351515484fb6)。

最新 [`backend/launcher.py`](https://github.com/triton-lang/triton-ascend/blob/main/third_party/ascend/backend/launcher.py) 已正确归一化常量参数路径：

```python
constant_paths = {
    key if isinstance(key, tuple) else (key,)
    for key in constants
}
```

并在 `_expand_signature` 中将对应位置改为 `constexpr`，保留 Python 输入位置，同时排除设备参数值。这比旧 #2387 补丁还覆盖 tuple、tensor descriptor 和嵌套参数路径。

因此，最新 main 在源码层面已包含本问题所需的处理，但本次未在 A5 上直接升级 latest main 重跑，不能将该源码检查写成 Qwen3.8 端到端实测通过。

活跃上游为 `triton-lang/triton-ascend`，本次检查时最后推送为 2026-11-19。`Ascend/triton-ascend` 镜像最后推送停在 2026-05-18，不能只检查该镜像判断最新修复状态。

### 9.3 没有包含该修复的正式发布版本

| 发布渠道 | 当前检查到的最新版本 | 是否包含修复 | 证据 |
|---|---|---|---|
| GitHub Release | [`v3.6.0.post2`](https://github.com/triton-lang/triton-ascend/releases/tag/v3.6.0.post2)，2026-10-29 | **不包含** | 仍使用旧 `driver.py::make_launcher`，设备打包只检查 `ty != "constexpr"`，没有 `constants` 过滤，也没有新的 `launcher.py` |
| PyPI | [`3.2.0`](https://pypi.org/project/triton-ascend/)，2026-01-21 上传 | **不包含** | 早于本问题的专门修复和 shared launcher 重构 |
| 上游 main | #2685 之后的源码 | **包含等价处理** | `argument_types/_expand_signature` 已处理常量参数路径 |

虽然 `v3.6.0.post2` 发布于 #2685 合入之后，但发布分支与 main 已分叉，不能用发布日期推断包含关系。专门修复 #2387 未合入，也不能作为任何正式版本已修复的依据。

当前环境应保留已验证的回移补丁；如果改用 #2685 之后的 main 源码，应重新验证与 torch_npu、CANN、vllm-ascend 的兼容性及本问题回归。若必须使用正式发行包，需要等待下一个实际包含 shared launcher 修复的 Release 或 wheel。

### 9.4 容易混淆但不相同的其他修复

- [#990](https://github.com/triton-lang/triton-ascend/pull/990) 和 [#1209](https://github.com/triton-lang/triton-ascend/pull/1209) 已合入，但解决的是“所有 kernel 参数均为常量”时 C++ 参数列表末尾逗号导致的编译错误，不处理本次设备参数错位。
- [`97b4e252ca7c`](https://github.com/triton-lang/triton-ascend/commit/97b4e252ca7cba9d0ca864b7645dcb52fceba215) 保留 pure-SIMT scratch 和 DTData 隐藏槽位，属于另一类 ABI 对齐修复，不等同于本次 value-folded 标量过滤。
