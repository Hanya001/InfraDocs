# 图模式是不是就是aclgraph？

- **不完全是。二者是“通用概念”和“具体实现”的关系。**

  - **图模式（Graph Mode）**：泛指把一系列算子及其依赖关系捕获成静态图，之后通过**整图重放**执行，减少 Python 调度和算子下发开销。
  - **ACL Graph**：昇腾 CANN 提供的具体图捕获与重放机制，类似于 NVIDIA 的 **CUDA Graph**。

  因此：

  - 在 **vLLM-Ascend** 等昇腾推理场景中，说“开启图模式”，通常就是指使用 **ACL Graph**，这时可以近似画等号。
  - 但 `torch.compile`、Inductor、FX Graph、TorchAir/GE 图等也叫“图”，**它们不等于 ACL Graph**。它们更偏向计算图表示、编译和优化；ACL Graph 更偏向已确定算子序列的运行时捕获与重放。
  - 实际系统还可能组合使用：先由 Inductor 等编译优化，再把可静态执行的部分用 ACL Graph 捕获重放；动态 shape 等不满足条件的部分仍可能回退到逐算子执行。

  一句话：**ACL Graph 是图模式的一种实现，但图模式不一定就是 ACL Graph。**



# 图模式有哪些关键概念？

图模式最核心的概念可以概括为：**捕获、实例化、重放、静态内存、固定形状**。在 vLLM-Ascend 中，还要特别理解**分段图、预热和回退**。

## 1. Eager 与 Graph：两种执行方式

- **Eager 模式**：每执行一个算子，CPU 就向 NPU 下发一次任务，灵活，但调度开销较大。
- **Graph 模式**：先把一串算子及依赖关系记录为图，之后一次性重放，减少 CPU 调度与算子下发开销。

图模式主要降低的是 **Host 侧调度开销**，并不意味着每个算子的计算本身都会变快。

## 2. 图捕获（Capture）

首次针对某种执行形状运行模型时，把算子执行序列、依赖关系、内存地址等记录下来：

```
正常执行一次
    ↓
记录算子及其依赖
    ↓
生成可重复执行的图
```



捕获期间通常要求执行过程是**静态、可重复**的，不能随意出现动态内存分配、Host 同步或不受支持的算子。

## 3. 实例化与重放（Instantiate / Replay）

- **实例化**：把捕获结果转换成设备可以执行的图对象。
- **重放**：后续请求不再逐个下发算子，而是执行整张图。

一次典型的解码过程类似：

```
static_input.copy_(real_input)  # 更新固定输入缓冲区
graph.replay()                  # 重放整张图
result = static_output          # 从固定输出缓冲区读取结果
```



因此，**捕获是准备工作，重放才是真正的加速路径**。

单次执行大致是这样

```
CPU：
  准备输入和运行时参数
  提交必要的图参数更新
  调用 graph.replay()
              │
              ▼
NPU：
  等待必要的输入和参数更新完成
  按图的依赖关系执行 Attention、FFN 等节点
  产生输出
              │
              ▼
CPU：
  在需要时同步、读取输出、调度下一次执行

```

**把原来每个算子都需要 CPU 参与的过程，压缩成每个推理步骤边界上的少量准备、更新和一次图提交；图内部主要由 NPU 自主按依赖执行。**



## 4. 静态输入输出与固定内存地址

图记录的是算子和内存地址之间的关系，所以重放时通常不能任意更换输入输出的内存地址。

一般需要：

- 预留固定的输入、输出缓冲区；
- 每次把真实输入复制到静态输入缓冲区；
- 重放后从静态输出缓冲区取结果；
- 中间激活和工作区也尽量保持固定。

这就是图模式经常需要 **static input/output buffer** 和显存池的原因。

## 5. 固定 Shape 与 Graph Key

传统整图重放要求捕获和重放时的关键执行条件一致，例如：

- batch size；
- sequence length；
- tensor shape；
- dtype；
- 某些控制执行路径的参数。

这些条件可以看作图的 **Graph Key**。条件不同，通常就需要另一张图：

```
(batch=1) → Graph A
(batch=4) → Graph B
(batch=8) → Graph C
```



为了减少图的数量，推理框架常采用：

- **Padding**：把小 batch 补齐到已捕获的大小；
- **Bucketing**：只选择若干预设规格捕获；
- **缓存**：保存并复用不同规格对应的图。

## 6. 预热（Warmup）

捕获前通常先正常执行若干次，用于完成：

- 算子和内存初始化；
- 自动调优与算法选择；
- 编译缓存加载；
- 工作区分配；
- 排除一次性操作。

否则，这些一次性行为可能发生在捕获期间，导致捕获失败或生成不可重放的图。

## 7. 整图与分段图

模型不一定能全部捕获。

- **Full Graph（整图）**：尽量把完整模型捕获为一张图，调度开销最低，但限制最多。
- **Piecewise Graph（分段图）**：把模型切成多个可捕获片段，不支持的部分仍用 Eager 执行。

例如：

```
图片段 1 → Eager 算子 → 图片段 2 → 图片段 3
```



分段图兼容性更好，但图之间的切换仍会产生调度开销。

## 8. 回退（Fallback）

当请求不满足已捕获图的条件，或者遇到不支持的算子时，框架可能：

- 换用另一张匹配图；
- 对输入进行 Padding；
- 回退到 Eager；
- 在允许的情况下捕获一张新图。

所以“开启图模式”不代表所有执行路径都一定走图，实际性能需要确认是否频繁回退。

## 9. 编译与图捕获不是一回事

以 Inductor 和 ACL Graph 为例：

- **Inductor**：侧重计算图优化、算子融合和代码生成；
- **ACL Graph**：侧重把已确定的设备任务序列捕获下来并重复执行。

二者可以独立使用，也可以组合：

```
Inductor 编译优化
        ↓
ACL Graph 捕获
        ↓
后续请求整图重放
```



## 10. 收益与代价

图模式更适合**算子数量多、单步 Host 调度开销明显**的场景，例如大模型自回归解码；同时也要付出：

- 捕获和预热时间；
- 额外显存；
- 多 Shape 图的维护成本；
- 动态执行路径受限；
- 输入复制和 Padding 开销。

一句话理解：**图模式就是先为固定执行路径和固定内存布局“录制”一张图，之后不断更换静态输入并重放它；Shape 越稳定、重放次数越多，通常收益越明显。**



# FULL_AND_PIECEWISE

## vLLM 中的几种图模式

| `cudagraph_mode`     | 纯 Decode batch | 含 Prefill 的 mixed batch                |
| :------------------- | :-------------- | :--------------------------------------- |
| `NONE`               | 不走图          | 不走图                                   |
| `PIECEWISE`          | 分段图          | 分段图                                   |
| `FULL_DECODE_ONLY`   | **整图**        | 不走整图，通常走未捕获的编译路径或 Eager |
| `FULL`               | **整图**        | 在后端支持时也走**整图**                 |
| `FULL_AND_PIECEWISE` | **整图**        | **分段图**                               |

当前官方稳定版 **vLLM-Ascend v0.30.0** 为例，常规默认配置是：

```
cudagraph_mode = FULL_AND_PIECEWISE
图捕获/重放机制 = ACLGraph（torch.npu.NPUGraph）
```

# Breakable 

**Breakable 是一种“不依赖 `torch.compile`，在运行时遇到指定断点就暂停图捕获、转为 Eager，然后继续捕获”的实现机制。**

和普通 PIECEWISE 的区别：

### 普通 PIECEWISE

由编译器提前拆：

```
torch.compile / FX
        ↓
在 Attention 等 splitting_ops 处拆图
        ↓
分别编译各图片段
        ↓
再交给 CUDA Graph 捕获
```

### Breakable

不经过 FX 编译拆分，而是在实际执行、捕获时拆：

```
原始模型 forward
        ↓
运行时遇到 @eager_break_during_capture
        ↓
结束当前捕获 → Eager 执行 → 开始下一段捕获
```

上游源码把它定义为：

> 用**运行时流捕获断点**替代基于 `torch.compile` 的 FX 图拆分。

官方实现见 [`breakable_cudagraph.py`](https://github.com/vllm-project/vllm/blob/main/vllm/compilation/breakable_cudagraph.py)，最初引入它的官方 PR 是 [#42304](https://github.com/vllm-project/vllm/pull/42304)

**Breakable 主要替代常规 PIECEWISE 中“依赖 `torch.compile`/FX 拆图”的实现，是一种可选的运行时分段捕获机制。**

- **它不是 `PIECEWISE` 必然具备的特性**，需要通过 `VLLM_USE_BREAKABLE_CUDAGRAPH` 等配置启用，并且模型中的操作要有相应断点支持。
- **断点由代码预先标记**，不是用户可以随意选择任意算子进行拆分。
- **它不只是换一个拆分器**：启用后通常还会绕过 vLLM 的 `torch.compile` 编译管线，因此也不再获得相应的 FX/Inductor 编译优化。

# 为什么 mixed/prefill 通常走 piecewise，而 uniform decode 更倾向 full graph？

**因为 uniform decode 更容易用少量整图保留高效的 Attention 执行路径，而且消除 CPU 下发开销的收益通常更明显；mixed/prefill 使用 piecewise，则能在复用 FFN 等图片段的同时，让 Attention 根据当前 batch 自由选择执行方式。**

**Uniform decode 指：一个 batch 里的请求都在进行解码，并且本次前向中，每个请求处理的 Query token 数量相同。**

投机解码的验证阶段也可能属于 uniform decode。例如每个请求都一次验证 4 个 token：

```
query_lens = [4, 4, 4]
```

只要这些请求都走相应的 decode/验证路径，而且每个请求的 Query 长度相同，就属于这种均匀 batch。具体后端是否支持该情形的整图，仍取决于实现。



## 我觉得在这个问题上有个盲区我一直没有意识到，导致我理解困难，你觉得是什么地方？

**你一直在以“请求、token”为单位理解执行，而图捕获的单位其实是“一次模型前向产生的设备任务”。尤其是，你可能下意识把 batch 看成了“几个请求各自跑一遍模型”，但实际通常是“把这些请求合并成一套算子来跑”。**

只看三个请求：

```
A：decode，当前处理 1 个 token
B：decode，当前处理 1 个 token
C：prefill，当前处理 128 个 token
```

**你可能直觉上想的是：**

```
A → 一条模型执行流水线
B → 一条模型执行流水线
C → 一条模型执行流水线

所以分别给 A、B、C 选择图模式就行。
```

**但常见的实际执行是：**

```
拼接这 130 个 token
        ↓
一次 QKV 投影
        ↓
一次或若干次 Attention 调用
        ↓
一次输出投影
        ↓
一次 FFN
        ↓
下一层
```

例如 FFN 是一次：

```
[130, D] @ [D, I]
```

这里并没有三个独立的 FFN 任务，只有一个同时处理三个请求的矩阵乘。

**所以图里记录的节点通常是“这一次矩阵乘”，不是“请求 A 的矩阵乘”“请求 B 的矩阵乘”“请求 C 的矩阵乘”。**一个节点可以同时处理多个请求。

这就带来两个关键结论。

**第一，“FULL 和 PIECEWISE”是在说任务序列的覆盖范围，不是在给请求贴标签。**

FULL： 把这次前向中的整套设备任务捕获起来

PIECEWISE：把这次前向的任务序列切成若干片段，部分片段捕获，Attention 等部分保留在图外

**第二，你说“变量更新一下就行”，这个判断本来就是对的，但它有一个前提：仍然执行同一套任务。**

比如：一次 Decode Attention + 一次 Prefill Attention就可能是不同的Attention操作



最有区分力的例子是：**固定总 token 数，改变请求组成。**

```
批次 A：128 个 decode 请求，每个 1 个 token
批次 B：1 个 prefill 请求，128 个 token
批次 C：64 个 decode 请求 + 1 个 64-token prefill 请求

三个批次的总 token 数都是 128。
```

对于 Dense FFN：

```
三个批次都是：
[128, D] @ [D, I] → 激活 → [128, I] @ [I, D]
```

**请求如何分组，对 FFN 没有意义。**因此，在地址、dtype 等捕获条件一致时，同一个按 128 token 捕获的 FFN 图片段就可以覆盖这些情况。

对于 Attention，请求分组直接决定计算关系：

| 批次 | Attention 要做的工作                               |
| :--- | :------------------------------------------------- |
| A    | 128 个单 Query，分别访问各自的历史 KV              |
| B    | 一个包含 128 个 Query 的序列，执行相应的因果注意力 |
| C    | 同时处理单 Query 解码与多 Query 预填充             |

后端为了高效执行，可能使用不同的分块策略、任务配置，甚至不同的 kernel 或调用次数。**只固定“总 token 数 = 128”，不足以保证这些高效路径都能由同一张图覆盖。**

这就解释了 piecewise 的价值：如果请求组成变化，FFN 等图片段可以仍按总 token 数复用，但是Attention在图外根据本次组成选择执行方案。

不过，这还不是全部原因。默认策略还有一个性能判断：

- **小 batch decode** 的设备任务往往较短，省掉逐层下发和图间衔接，收益比较明显。
- **较长 prefill** 的设备计算通常更重，保留高效 Attention 路径的价值可能高于进一步减少 Host 下发的收益。

所以这里有两层判断：

1. **能否复用整图**：后端是否能在固定任务结构下，正确处理不同 Query 分组和 KV 状态？
2. **复用是否划算**：为统一图而采用的执行路径，是否比图外选择专用路径更快？

**如果 Attention 后端能用一套高效、图兼容的路径覆盖 mixed/prefill，那么这些场景完全可以走 FULL。**因此你的理解可以收敛为：

> **mixed/prefill 的 Attention 执行方案更依赖请求组成；piecewise 把这部分变化留在图外，让其他部分继续复用。Uniform decode 的组成更规律，而且通常更需要降低下发开销，所以更倾向 FULL。**

这比“Attention 的 Shape 动态，所以不能入图”准确得多。



## Uniform Decode 的 QKV 与 Attention 如何一起计算

多个 uniform decode 请求会把各自当前 token 的隐藏状态拼成一个矩阵，例如 3 个请求得到 `[3, D]`；随后用同一套权重一次完成融合 QKV 投影。矩阵乘的每一行只对应一个 token，因此请求之间的数据不会混合。这一步与 FFN 类似，本质是把多个请求合并成更大的矩阵乘，以提高计算效率。

新算出的 Q/K/V 只是本步 token 的结果。框架会按各请求的位置把新 K/V 写入分页 KV Cache，并用 `block_table` 记录逻辑 KV 块到物理块的映射。各请求历史长度可以不同，例如 `[101, 501, 2001]`；这些信息由 `seq_lens` 表达，并不要求把 KV Cache Tensor 改成不同 Shape。

Attention 虽然只提交一次算子，但每个请求的 Query 只访问自己的历史 KV，并通过 `block_table` 和有效长度隔离。因此可以说它们“一起调度、并行计算”，但不会相互做注意力。

图模式之所以能够重放，是因为固定的是缓冲区地址、任务结构和支持的 Shape；每步变化的当前 token、KV 内容、有效长度和页表映射，通过更新固定缓冲区或设备 metadata 表达。不同请求的历史长度可以持续增长，但 KV Cache 容量和 Captured Task 不需要随之重建。如果后端仍依赖 Host 侧长度或需要更换任务参数，就用 graph task update 刷新；如果遇到不同执行路径，则分桶、换图或回退。

核心结论：**FFN 和 QKV 投影容易复用，是因为它们按 token 行独立计算；Attention 的复杂性来自请求级 KV 访问和执行路径。Uniform decode 把“每个请求本轮 Query 长度”固定住，使这条路径更稳定，因此更适合整图重放。**
