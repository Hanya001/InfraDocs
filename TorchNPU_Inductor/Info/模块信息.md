# 基础信息

## torch 2.15.0+与 torch_npu ascend pytorch是什么关系？

**torch 和 Ascend/pytorch 仓的关系是：torch 是华为从 PyTorch 官方仓 fork 出来的上游基底，Ascend/pytorch 仓是 torch_npu 适配层的开发仓，两者是「本体与插件」的关系，不是同一个东西。**

### 具体拆开说

**torch 本体**（pytorch/pytorch 官方的 `torch` Python 包）：PyTorch 框架本身。我们环境里装的是官方发布的 CPU 版安装包（如现在的 2.13.0+cpu，路径升级后是 2.15.0+cpu），它的 `_inductor/` 目录是 GPU/CPU 的 Inductor 实现，不含任何 NPU 内容。

**Ascend/pytorch 仓**（即 torch_npu 的源码仓）：华为维护的 NPU 适配层，核心产物是 `torch_npu` 这个 Python 包。它的内容是 NPU 设备接入、算子路由到华为的 aclnn 算子库、以及 `_inductor/triton_experimental/` 这个 NPU 编译后端。torch_npu 以外挂方式 import 进 torch，不修改 torch 本体。仓里的 git 历史是从 PyTorch 官方仓 fork 出来的（所以分支名带 pytorch 版本号），但构建产物 torch_npu 只包含适配层。

### 耦合方式

torch_npu 对 torch：挂在算子分发层，torch 被动接受

torch 的架构里有一个算子分发器（dispatcher）：每个算子调用进来，分发器根据张量所在的设备选择实现。torch 为第三方硬件在这里留了一个通用槽位，叫 PrivateUse1 分发键——torch 本体代码里没有任何一处出现「npu」字样，但任何第三方设备都可以把自己的算子实现注册到这个槽位上。torch_npu 就是这个机制最大的使用者。

具体过程是：`import torch_npu` 这一句执行时，torch_npu 的初始化代码向 torch 注册 npu 这个设备类型，然后把几百个 aten 算子（加、减、卷积、注意力……）的 NPU 实现逐个挂到分发键上，同时接管设备管理、张量搬运这些入口。此后你写 `x.to("npu")` 或在 NPU 张量上做任何运算，分发器自然把调用送到 torch_npu 的实现上。**torch 自始至终不知道 NPU 存在**：不 import torch_npu，torch 在昇腾机器上就是一个纯 CPU 库，行为完全不变。激活权完全在插件一侧。

torch.compile 这层稍深一些：Inductor 的代码生成是设备相关的，torch_npu 通过自己仓里的 `_inductor` 目录加一个 `npu_backend` 配置键把 triton_experimental 接进来——这仍然是使用 torch 预留的扩展点，不改 torch 一个字节。

torch_npu 的握手发生在**运行时 import 的一刻**，挂在 torch 的 C++ 分发层和 Python 枚举别名上，不 import 就完全不存在。

### 版本号对齐

**版本号 `2.15.0+gita8a5c51` 这类写法的含义**：torch_npu 的版本号跟随 torch 的版本号走——torch_npu 2.15 意思是「给 torch 2.15 用的适配层」，`+git<hash>` 是构建时自动附上的源码提交标注。同版本号的两边必须接口匹配：torch_npu 编译时会校验 torch 版本，且 master 分支的 torch_npu 源码是按它 fork时点的 torch master（现在即 2.15）的接口写的。

**所以「torch_npu pin 到 master」实际是三件事的组合**：torch 本体换成 2.15.0+cpu（pip 装），torch_npu 用 master 源码对着这个 torch 2.15 编译，两者版本号对齐为 2.15。之前查过的那个事实在这里起作用：官方 master 的 torch_npu 在 9 月 17 日做过「adapt to torch 2.15 signature changes」的适配——master 的 torch_npu 现在期待的就是 torch 2.15，所以路径一里 torch 本体必须跟着上 2.15，否则编译不过。



## vLLM 与 vLLM-Ascend 的关系详解

### 各自是什么

**vLLM** 是开源的大模型推理引擎本体，托管在 GitHub 的 vllm-project 组织下。它负责推理服务里与硬件无关的全部：请求调度、连续批处理（continuous batching）、PagedAttention 式的 KV 缓存管理、采样、投机解码框架、以及编译配置框架。它以 pip 安装包（wheel）形式发布，官方发布物只保证 CUDA 平台。

**vLLM-Ascend** 是同一个组织下的姊妹仓库（github.com/vllm-project/vllm-ascend），由华为团队主导开发，把 vLLM 移植到昇腾 NPU。它发布的包叫 vllm_ascend，内容全部是昇腾专属实现，不包含 vLLM 本体的任何代码。类似的平台插件仓在 vllm-project 组织下还有若干个（Intel Gaudi 等硬件各一个），「主仓 + 平台插件仓」是 vLLM 社区的标准硬件接入模式。

VLLM和torch_npu做法不同， 它把推理引擎按职责切成一组组件基类——Platform（平台能力描述）、Worker（进程与设备管理）、ModelRunner（每步前向的执行）、AttentionBackend（注意力实现）等——并在自己的安装包里声明了一套插件发现机制：vLLM 启动时扫描已安装包里注册到 `vllm.general_plugins` 入口组的插件并调用其初始化。

vllm-ascend 的接入是**整个组件级别的替换**：它的 AscendPlatform 类实现平台接口，NPU 版的 Worker 和 ModelRunner 继承主仓基类替换掉 GPU 版，注意力后端从主仓的后端注册表里挂入自己的实现。主仓代码里遍布着「向当前平台询问」的调用点（比如问当前平台编译后端怎么配、图捕获用哪种），运行到这些点时控制权交给插件的实现。

### 版本怎么对齐

vLLM-Ascend 通过所谓 main2main 的同步管线跟随上游：上游 vLLM 每发一个版本，vLLM-Ascend 跟着发一个同号版本（vLLM-Ascend v0.27.1rc 对齐 vLLM 0.27.1，v0.30.0 对齐 vLLM 0.30.0，都是隔几天到几周跟进）。它的依赖文件里 pin 了配套的 vLLM 版本、torch/torch_npu 版本、triton-ascend 版本和 CANN 版本，整套构成一个官方验证过的组合。

### 插件怎么挂进本体：五个接入层

vLLM 主仓为平台插件预留了插槽，vLLM-Ascend 的代码就插在这些插槽上：

1. **平台注册层**（vllm_ascend/platform.py 的 AscendPlatform）。vLLM 启动时探测硬件，发现 NPU 后加载昇腾平台的实现。这一层决定很多平台级行为，最典型的是编译后端选择：`_setup_compile_backend()` 函数把 vLLM 的编译配置改写成 `use_inductor=False`，换成昇腾自己的编译方案。
2. **Worker 层**。vLLM 主仓定义了 Worker 抽象（每个进程管理一张卡、执行模型前向），昇腾侧有对应的 NPU Worker 实现，负责设备初始化、模型加载和显存管理。
3. **注意力后端层**。vLLM 把各种注意力实现抽象成可替换的后端，昇腾侧提供走华为 aclnn 算子的注意力实现，MLA 等特殊注意力也在这里路由。
4. **自定义算子层**（C++ 扩展）。vLLM-Ascend 仓库的 csrc 目录里有自己的 C++ 扩展，编译出昇腾优化的算子（量化、归一化融合等），注册进 PyTorch 的自定义算子机制——为避免与 CANN 自带算子重名，这些算子统一带 `_vllm` 后缀。这一层是纯编译产物，所以构建顺序上必须等 torch_npu 就绪后才能编它（它链接 torch_npu 的头文件和库）。
5. **图模式与编译层**。vLLM 主仓有分段编译框架（把模型切成段，注意力段 eager 执行、其余段编译）和 CUDA Graph 捕获框架；昇腾侧的对应物是 ACLGraph（昇腾的整图录制回放，对标 CUDA Graph）和一套 FX 图上的算子融合 pass（GraphFusionPassManager），FULL 模式还引入源自 torchair 的 npugraph_ex。

### 运行时的组合方式

实际部署就是装两个包：vLLM 本体的 wheel 加 vllm_ascend 的 wheel。启动 vLLM 时它自动发现 NPU，加载昇腾平台实现，请求调度、批处理这些主仓逻辑原样运行，凡是碰到设备相关的调用都落到 vllm_ascend 的实现上。所以**功能是主仓给框架、插件给血肉**：模型支持面（哪些模型能跑）主要由主仓的模型代码决定，能不能在 NPU 上跑得对、跑得快主要由插件层决定。

vllm-ascend 的握手发生在**pip 安装时写下的元数据**里，挂在纯 Python 的入口组和类继承上，装了就被 vllm 按组发现。

## triton-ascend

### triton-ascend 与 bisheng关系

**triton-ascend 是 Triton 编译器的昇腾后端，bisheng（准确名字是 bishengir-compile，仓库叫 AscendNPU-IR）是它内置的底层 MLIR 编译器——bishengir 以 git 子模块的形式住在 triton-ascend 仓库里面。** 两者不是并列的两个项目，而是「后端外壳 + 内置引擎」的包含关系。

仓库结构可以直接看到这个包含关系（triton-ascend main 分支的树）：

```
triton-ascend/
├── python/                  # Triton 语言与前端（上游共用）
├── third_party/ascend/
│   ├── backend/             # 昇腾后端主体（Triton IR → 昇腾的映射代码）
│   ├── ascend_ir.cc         # 对接层
│   └── AscendNPU-IR/        # ← bishengir-compile，git 子模块
```

### 在编译链里各管哪一段

整个链条从上到下是：torch.compile 选 `npu_backend=triton_experimental` → torch_npu 的 triton_experimental 生成 Triton kernel 源码 → Triton 前端把它变成 MLIR 中间表示（TTIR/TTGIR）→ **triton-ascend 后端**接管 → **bishengir** 完成底层优化和代码生成 → CANN 运行时把二进制加载到 NPU 执行。

**triton-ascend 管的是「翻译」**：Triton 的抽象是按通用 GPU 设计的（线程块、共享内存、以 CUDA 为原型），昇腾硬件的执行模型不同（AI Core、unified buffer、cube 向量标量单元分离）。triton-ascend 的 backend 目录负责这段翻译——计算网格怎么映射到昇腾的核心阵列、Triton 的共享内存语义落到哪个层级的存储、自动调优的候选怎么生成和实测。

**bishengir 管的是「优化和落地」**：接到翻译结果后做底层 MLIR 优化并生成硬件二进制。它的优化能力就是本项目性能文档里研究过的那些编译器特性——AutoBlockify（逻辑块到物理核的折叠，之前有专门报告澄清过它的真实含义）、AutoFlatten、AutoSchedule、多缓冲流水等。之前性能配置项实测得出的那条结论「bisheng 已自动覆盖常见的访存优化，在 Inductor 层叠加同类配置收益低」，说的正是 bishengir 这层的自动 pass 在起作用。

**CANN 管的是「运行」**：bishengir 只负责把代码编成二进制，二进制要在硬件上跑起来靠 CANN 的运行时和驱动接口。所以 CANN 版本同时约束两边——triton-ascend 3.6.0 要求 CANN 9.2.0 起，本质是「生成的指令要跟运行时接口匹配」，这也是升级方案里 CANN 9.2 镜像是前置条件的原因。

### 中间表示文件：编译过程的记录

**.ttir** 是 Triton 通用中间表示（MLIR 文本格式），由 Triton 前端从 kernel 的 Python 源码生成，内容是硬件无关的计算描述。

**.ttadapter** 是 triton-ascend 后端接手后产出的昇腾适配版中间表示——后端在这一步完成昇腾特有的变换（访存布局、块映射、昇腾方言的转换），然后把它交给 bishengir。

**.npubin 是真正的编译结果**：bishengir 生成的昇腾 AI Core 机器码，对应 CUDA 后端的 .cubin。kernel 到这一步就变成了硬件可直接执行的指令序列。

**.so 是宿主侧的 kernel 启动器**：每个被实际调用的 kernel 配一个小型 C++ 动态库，负责在 Python 调用时装载参数、通过 CANN 运行时接口把 npubin 下发到设备执行。Python 侧看到的「调 kernel」最终落在这个启动器上。

# 特性信息

### 一、编译入口：让 Inductor 能被选中（先决条件）

vllm-ascend 的 platform.py 默认强制 `use_inductor=False` 并指向自研的 AscendCompiler。接入的第一步就是在 `_setup_compile_backend()` 里增加一条 Inductor 路径：让 vLLM 的 `-cc.backend inductor` 能透传到 `torch.compile(backend=triton_experimental)`，同时逐项修正 vLLM CompilationConfig 里与 NPU 不兼容的默认值（如 `use_inductor_graph_partition`）。本地在这上面的最终形态是把入口从私有配置键移回 vLLM 标准参数——这样新版本升级时改动面最小。

### 二、图捕获：让分段编译与 ACLGraph 对接

vLLM 的分段编译把注意力留 eager、其余段编译，昇腾的 ACLGraph 要和这套分段结构组合（PIECEWISE 默认、FULL 整图可选）。两个具体点：分段点要按架构补充（MLA、DSA 这类注意力必须加额外分段点，否则图捕获不健康）；特殊算子的 fake 实现/注册要齐，否则进不了图。

#### 编译和图捕获区分

编译和图捕获解决的是两个不同层面的问题，而且“编译”这个词容易让人以为编译完就会一次性执行，其实不是。

先分清两种“图":

1. **计算图**（FX graph）：模型的运算关系，比如“先做矩阵乘，再加 bias，再过 SiLU 激活”。这是编译器看到的中间表示，它是**静态的、描述性的**。
2. **捕获图**（CUDA Graph / 昇腾上的 ACLGraph）：把一段**实际执行过程**（一串 kernel 的启动指令）录下来，之后一次提交、整段回放。它是**运行时的、录制出来的**。

编译处理的是第一种图，图捕获处理的是第二种图。

拿一个很小的模型举例，假设计算是 `matmul → add → silu`：

| 状态                       | 实际发生什么                                                 | 快在哪、慢在哪                                      |
| -------------------------- | ------------------------------------------------------------ | --------------------------------------------------- |
| 纯 eager（不编译、不捕获） | 三个算子各自启动一次，共 3 次 kernel 启动                    | `add` 和 `silu` 是两次很小的启动，开销占比高        |
| 只编译、不捕获             | Inductor 把 `add` 和 `silu` 融成一个 kernel，变成 2 次启动；每次请求仍然走 Python wrapper | kernel 变少了，但每次请求仍有启动和 Python 调用开销 |
| 编译 + 捕获                | 在上一行基础上，把这一整段（以及前后几十个算子）录成一张图，之后一次提交整段回放 | kernel 少，启动开销也几乎消失                       |

#### 捕获模式

| 取值                 | 这一步的计算怎么打包                                         | 适合什么情况                                         |
| -------------------- | ------------------------------------------------------------ | ---------------------------------------------------- |
| `NONE`               | 不录制。每一步都直接调用编译产物，逐个 kernel 启动           | 调试、基准对照，也用于第一阶段“只验证编译正确性”     |
| `PIECEWISE`          | 模型按 attention 位置切成若干段，每段按 batch size 档位各录一张图；attention 本身不进图，每次现场执行 | 形状变化大、批内 prefill 和 decode 混合的步          |
| `FULL`               | 不切段，整个 forward 连同 attention 一起录成一张图           | 形状固定、步数占比最高的 decode 步                   |
| `FULL_DECODE_ONLY`   | 每步先判断：全是 decode 步就按 FULL 走；出现混合批就完全不录制，现场逐段执行 | 只想要 decode 的整图收益，但不愿意为混合步付录制成本 |
| `FULL_AND_PIECEWISE` | 每步先判断：全是 decode 步就按 FULL 走；混合批按 PIECEWISE 走 | 两类步都要，decode 拿整图收益，混合批保留分段兜底    |

![image-20261109165723553](./assets/image-20261109165723553.png)

切成这样的原因：attention 的输入长度随请求变化很大，图捕获要求形状和显存地址固定，所以把它留在编译段外面，每次正常执行。切点两侧的段形状相对固定，适合编译和捕获。

#### 数据流动方式

```
模型 forward（Python 函数）
  │ torch._dynamo 抓取
  ▼
FX 图（整张，torch.fx.Graph）
  │ vLLM 的 split_graph 按 splitting_ops 切段
  │ attention 类算子留作边界子图，不进编译
  ▼
FX 图 1…N（29 段）
  │ vLLM 的 make_compiler 读 compilation_config.backend
  │ "inductor" → InductorAdaptor（上游 vLLM），不经过 AscendCompiler
  │ 空串 → AscendCompiler（vllm-ascend），内部分 npugraph_ex / fusion_pass
  ▼
InductorAdaptor（上游 vLLM）
  │ 把平台钩子提供的 AscendPostGradPassManager 挂进 Inductor 配置
  ▼
torch._inductor.compile_fx
  │ AOTAutograd → post-grad pass（执行昇腾融合 pass）
  │ → 代码生成（TORCHINDUCTOR_NPU_BACKEND=triton_experimental
  │   选中 torch_npu 后端）
  ▼
编译产物（每段一个 wrapper + kernel 二进制）
  │ vLLM 用平台钩子取到 ACLGraphWrapper，逐段包一层
  ▼
ACLGraphWrapper(段 1) … (段 N)
  │ 预热阶段逐段、逐 batch size 档位执行并录制
  ▼
ACLGraph × 档位（29 × 5 = 145 张）
  │ 请求到来，按当前 batch 查表
  ▼
回放（没命中档位就直接调编译产物）
```

### 三、融合与量化：vllm-ascend 自己的 pass 挂进 Inductor 管线

vllm-ascend 有三条 FX 图上的算子融合 pass（RMSNorm+量化一类），要让它们在 Inductor 路径下默认启用、通过 vLLM 的 `inductor_passes` 机制与 Inductor 自己的 pass 协同工作。W8A8 量化的 pattern 也要适配 Inductor 的代码生成路径。

### 四、编译缓存与调优时间：让启动可用

不处理缓存复用，每次启动 vLLM 都要重新编译全部 kernel（冷启动五百秒量级）。本地补了编译缓存跨启动复用的两个环节，把复用启动压到一分钟内。autotune 同理——每个 kernel 多候选实测会把编译窗口拉长，需要候选集治理（本地把每 kernel 候选从 11.5 个压到 3.5 个）。

### 五、特性级验证：每个 vLLM 特性单独过编译路径

这是工作量最大的部分——每个特性在编译路径下都是新的组合，本地按此建了 272 个用例的门禁。已验证的结果可供参照：

| 特性                                 | 状态与要点                                            |
| ------------------------------------ | ----------------------------------------------------- |
| W8A8 量化                            | 已验证且解码性能反超原有方式                          |
| W4A8                                 | 冒烟通过                                              |
| fp8 / mxfp8                          | eager 层就崩，属平台问题，与接入无关                  |
| 投机解码（eagle3/dflash/ngram/MTP）  | 逐 token 与 eager 输出一致，已验证                    |
| MoE / MLA / 线性注意力 / 16K+ 长序列 | 已验证，注意 MLA 与 DSA 的分段点                      |
